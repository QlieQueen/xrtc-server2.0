# v2_15.x 多 worker 拉流分发架构 — 章节总览

> 2026-09-01 Phase 12 开局讨论落盘。起因：我问"15.x 是干什么的"，答：**为了多线程拉流——不能把同一条推流的所有拉流端都钉死在一个 worker 线程上，否则 1V 超级多时就是"1 核有难，8 核围观"**。验证后发现一击命中。

## 问题：stream_name 哈希的负载瓶颈

改造前（Phase 0~11 一直如此）：

```cpp
// rtc_server.cpp — 所有消息一律按流名哈希
RtcWorker* worker = GetWorker(msg->stream_name);  // CRC32(stream_name) % N
```

这个路由的隐含契约：**同一条流的所有消息（push + 它的全部 pull）永远落在同一个 worker 线程**。

好处是"同流消息有序"免费获得——manager 里 FindPushStream、RTP 广播、NACK 查缓存全部是同线程内存操作，零锁零拷贝。

代价在 1V多 场景爆炸：一条热门流 1 推 100 拉，RTP 扇出、100 份 SRTP 加密、NACK/RTX 重传、100 份 RTCP 全压在 1 个线程上，其余 worker 全闲。吞吐上限 = 单核。

## v15.2 解法：拉流侧改按 uid 哈希（仅 20 行）

```cpp
if (msg->cmdno == CMDNO_PULL || msg->cmdno == CMDNO_STOPPULL ||
        (msg->cmdno == CMDNO_ANSWER && msg->stream_type == "pull")) {
    worker = GetWorker(msg->uid);          // uid % N，拉流端打散到所有 worker
} else {
    worker = GetWorker(msg->stream_name);  // 推流仍按流名
}
```

三个设计点：

1. **推流不动**：一条推流只占一个 worker，按流名哈希天然把不同推流散开，没有单点问题
2. **uid 粘性**：同一拉流端的 PULL/ANSWER/STOPPULL 全落 `uid % N` 同一 worker——单条拉流的消息有序性保住；打散的只是"不同拉流端"之间的负载
3. **ANSWER 按 stream_type 分流**：pull 的 answer 必须送到 uid 哈希的 worker（PullStream 在那），push 的 answer 送到流名哈希的 worker（PushStream 在那）

## 这 20 行是颗雷：manager 四大依赖点全部跨线程化

| 依赖点 | 单线程时代（免费） | 跨 worker 后（崩溃） |
|----|----|----|
| 拉流找推流 | FindPushStream 本地 map 直查 | pull 在 worker B，push 在 worker A，B 的 manager 没有这条推流 |
| RTP 广播 | push 同线程遍历 multi_pull_streams_ 调 SendRtp | 跨线程调 = 数据竞争 |
| NACK→RTP Cache | 拉流端 NACK 直查本 worker 的 PushStream 2048 槽缓存 | 缓存在推流 worker，请求从拉流 worker 来 |
| PLI / SR 时间线透传 | 同线程 signal 一路捅到底 | 全部变跨线程 |

**分发路由改一行，管理层要从"线程内对象图"重构为"跨线程消息协作"** ——这就是 15.3~15.12 约 500 行全砸在 rtc_stream_manager 上的原因。

## v15.3 起的重构方向（已核实）

- Manager 自建 **pipe + IOWatcher + Notify**（与 RtcWorker 同款跨线程唤醒套路：生产者写 lock-free queue + 写 pipe 一个 int，消费线程 pipe 可读后 drain 队列）
- 引入 `mutex` + `lock_free_queue.h`
- 定义 **ComMsg**（跨 manager 信使）：`msg_type / worker_id / uid / stream_name / audio_source / video_source`

推测后续课程主线：订阅关系建链（pull worker → push worker 发 ComMsg 注册）、RTP 广播跨线程投递、NACK/PLI/SR 沿新链路重接。逐课核实时更新本文。

## 面试表达主线

> "单线程 per-stream 模型在 1V多 下会退化成单核瓶颈。我们把拉流侧路由从流名哈希改成 uid 哈希，负载打散了，但代价是原来靠线程绑定免费的四类同流操作（查找/广播/缓存/控制信令）全部跨线程化——所以真正的工程量不在路由那 20 行，而在管理层从对象图到消息协作的重构。这是个典型的'用一致性模型换水平扩展'的 trade-off。"

对比业界：mediasoup 也是 worker 进程 + router 绑定模型，热门 router 同样会单 worker 过载（官方用 multi-port / 级联缓解）；LiveKit/Janus 按 participant/session 分发。共识都是：**会话内有序用绑定，会话间负载用哈希打散**。
