## 一、问题：上行 RTP 被"原样、立刻"转发下行

一推多拉 live 模式的转发链（**推流端 → 服务器 → 拉流端**）：

```
上行 RTP → PC::OnRtpPacketReceived（live 分支）
  → video_receive_stream_->OnRtpPacket
  → RtpVideoStreamReceiver::OnRtpPacket：
      ① config_.rtp_rtcp_module_observer->OnRtpPacket()  ← 立刻、按到达顺序往上抛
      ② ReceivePacket()                                   ← 组帧路径（有序的是"帧"，不是"包"）
      ③ rtp_receive_stat_->OnRtpPacket()                  ← 统计（排除 recovered）
  → ①的 observer = PC 自己（peer_connection.cpp:586/618 config.rtp_rtcp_module_observer = this）
  → PC::OnRtpPacket → SignalRtpPacket → PushStream::OnRtpPacket
  → listener_ → RtcStreamManager → 广播给所有拉流端
```

关键点：**第 ① 步不做任何排序/去重/缺口处理**——每个包一到就按到达顺序抛给上层，上层也原样广播。`ReceivePacket`（②）走的是服务器自己的组帧/统计链路，**和转发是两条路**，PacketBuffer 的有序性帮不到下行转发。

## 二、下行看到什么：乱序 + 缺口

### 2.1 乱序来源 1：网络上行乱序

推流端到服务器的网络存在抖动/重路由，包 N+1 可能先于 N 到达。服务器按到达顺序广播 → 拉流端看到 `…, N-1, N+1, N+2, …`。

### 2.2 乱序来源 2：RTX 恢复包天生"迟到"（重点）

上行丢包后，服务器靠 6.x 的 NACK/RTX 恢复：N 丢了 → 先收到并转发了 N+1、N+2 → N 被 RTX 重传回来后**同样走 ① 转发**（代码注释"包含正常的包和 rtx 重传包"，只有 ③ 统计把 recovered 排除掉）。

```
上行实际到达：N-1, N+1, N+2, N（N 由 RTX 补回）
下行广播顺序：N-1, N+1, N+2, N   ← 缺口先露出来，N 最后才补
```

即：**即使上行恢复成功，下行看到的也是"先缺后补"**。

### 2.3 缺口来源：上行真丢包

RTX 也救不回的包（RTX 本身丢失 / 超出 NACK 窗口 / 超时）永远不会到服务器，下行看到的缺口是**永久性**的。

## 三、后果：拉流端无效 NACK + 服务器 RTX 风暴

- 对"只是迟到、最终会到"的包，拉流端也会发 NACK（它不知道服务器手里有）
- 服务器 10.x 的缓存命中 → 重传 → 拉流端又收到一遍 → 反而制造更多乱序 → **NACK 正反馈**
- 实测就是 `v2_10.7`：云上 1推2拉，下行带宽爆到 10M、RTX 占 30%，裸重传无节流
- 对"真丢"的包：拉流端 NACK 无果 → 只能等下一个关键帧自然出现 → 弱网下长时间花屏

一句话：**服务器不加处理就把上行乱序/缺口透传下去，等于把上游的网络问题放大给所有拉流端，还叠加了自己的 RTX 风暴。**

## 四、解决方向：v12.3 连续性控制 + v12.4 关键帧重启

### 4.1 v12.3：PushStream::ProcessVideoPacket —— 转发前排序缓冲

在**广播点**（PushStream::OnRtpPacket）对视频包做连续性控制，音频仍直接广播：

```
新成员：video_seq_      已转发的最大连续 seq
        first_seq_time_ -1 = 还没收到第一个包（状态标志）

OnRtpPacket：视频 → ProcessVideoPacket(new_packet)；音频 → 直接广播
ProcessVideoPacket：
  1. 先 CacheVideoPacket（10.x 的 2048 槽缓存照旧，供下行 NACK 重传）
  2. 首包（first_seq_time_ == -1）→ video_seq_ = seq，立即广播
  3. 重复/落后（AheadOrAt(video_seq_, seq)）→ 丢弃（含 RTX 造成的二次到达）
  4. 缺口（seq != video_seq_ + 1）→ 只缓存、压住不转（乱序/缺口的包等补齐）
  5. 有序 → 从该 seq 起向后扫缓存，连续转发到断档为止（上限 kVideoPacketCacheSize=2048），
     video_seq_ = 最后转发的那包
```

效果：**只有连续的一段才向下广播**。缺口被补齐（网络迟到的包 / RTX 恢复包到达）时，一口气把压住的连续段全发出去；拉流端拿到的是干净有序的流，几乎不需要自己发 NACK。

### 4.2 v12.4：完整 IDR 帧重启 + 清缓存 —— 缺口补不上的兜底

连续性控制的代价：**若缺口永远补不上（真丢包），转发会一直卡住，下行停摆**。兜底机制：

```
PC::OnFrame 增加 SignalFrame（帧组装链路 5.x 已具备：PacketBuffer → RtpFrameObject → PC::OnFrame）
PushStream::OnFrame：
  1. 只认关键帧（frame_type() == kVideoFrameKey）
  2. 关键帧起点 start_seq_num 必须领先 video_seq_（AheadOf，防倒退/防重复处理）
  3. 从 start_seq_num 起扫缓存连续转发（拉流端拿到新 IDR 即可出画）
  4. ClearVideoPacketCache(video_seq_+1, start_seq_num-1)：清掉旧区间缓存
     —— 旧包已被新关键帧取代，不清会导致拉流端 NACK 命中后做无效重传
  5. video_seq_ = 最后转发的包
```

配合 8.x 的 PLI：拉流端请求关键帧 →（服务器转发）→ 推流端出 IDR → 服务器重启下行。缺口恢复 = **等关键帧，而不是等缺的那个包**。

### 4.3 三件套配合关系

| 模块 | 解决的问题 | 时机 |
|------|-----------|------|
| 6.x 上行 NACK/RTX | 服务器自己收齐上行（缺口能补则补） | 上行恢复 |
| 10.x 下行 RTP Cache + NACK 重传 | 服务器有包、拉流端缺包（缓存命中→RTX 单播） | 下行恢复 |
| 12.3 连续性控制 | 服务器把上行乱序/缺口捋顺再广播（防无效 NACK + 风暴） | 转发前 |
| 12.4 关键帧重启 | 上行真丢包、缺口永远补不上时，从新 IDR 重启下行 | 兜底恢复 |

## 五、为什么排序点选在 PushStream 广播点

1. **一个出口服务 N 个拉流端**：在广播点排一次序，N 路全部受益；若在每路 PullStream 各自排，重复且不一致
2. **服务器自己的接收链不需要这个排序**：组帧路径有 PacketBuffer 兜着（5.x），统计路径只关心累计指标
3. **排序语义正好落在"SFU 边界"**：服务器内部怎么乱都行，**出网口的流必须干净**——这是 SFU 对下游客户端的基本承诺，也是下游不需要大 jitter buffer 的前提
4. 16 位 seq 比较必须用 `AheadOf/AheadOrAt`（回绕感知），不能写成 `seq < video_seq_`——回绕后数值大小反转（见 v2_6.1 的坑）
