# v2_11.5 XR/DLRR 协议定义与 libwebrtc 实现辨析

本节内容: 11.2~11.4 已打通 XR 发送(RRTR)/接收(DLRR)算 RTT 的骨架与填实,
本节 11.5 收尾两件事: **register_ssrcs_ 过滤 DLRR 子块** + **OnRttUpdate 上报 RTT**。
本文档记录讨论中理清的观点(协议层 vs 实现层), 供面试/复习引用。

## 0. 一句话总结

- **协议层**(RFC 3611 §4.5): DLRR 名字里的 "RR" 就是经典的 **Receiver Report(201 号报文)**, 这个 XR 块天生就是报告"我收到过谁的 RR"。
- **实现层**(libwebrtc / 本工程): RR(201) 报文里**没有时间戳**, 所以实现用 **XR(RRTR) 的 NTP 时间戳**充当"RR 到达时刻"——收到 RRTR 才回 DLRR, last_rr 填 RRTR 的 NTP。
- 两者不矛盾: 协议规定统计的是 "RR 到达", 实现用 RRTR 给 RR **补了一个钟**。

## 1. 核心辨析一: DLRR 里的 "RR" 是 201 号 Receiver Report

RFC 3611 §4.5 定义 DLRR = **Delay since the Last *Receiver Report***。每个子块三个字段:

| 字段 | 含义 |
|------|------|
| `ssrc` | **谁发的那个 RR**(RR 的 sender ssrc) |
| `last_rr` | 收到那个 RR 的时刻 |
| `delay_since_last_rr` | 距离现在过了多久(1/65536 秒单位) |

本端 rtcbase 头文件直接印证: `dlrr.h` 注释 "DLRR Report Block: Delay since the Last Receiver Report (RFC 3611)", `kBlockType = 5`。

## 2. 核心辨析二: 实现为什么扯上 RRTR(协议与实现的分歧点)

协议说 last_rr 是 "RR 到达时刻", 但 **RR(201) 在线上没有任何时间戳字段**, B 无法在 DLRR 里填 "那个时刻"。

libwebrtc 解法: 用 RRTR 充当参考钟——

- A 发 `RR + XR(RRTR)`, RRTR 里带一个 NTP 时间戳
- B 收到 RRTR 后, 把这个 NTP **原样回填**进 DLRR 的 last_rr
- A 再算 `RTT = now − last_rr − delay`(now 是 A 的钟, last_rr 也是 A 自己的钟 → **同钟相减, 消掉时钟偏差**)

对应代码: libwebrtc `rtp_rtcp_impl2.cc:286 ConsumeReceivedXrReferenceTimeInfo()`, **收到 RRTR 自动回 DLRR, 无条件**。

> 所以观察到的现象 "收到 RRTR → 回 DLRR" 是实现的表象; 协议语义上 DLRR 报告的对象仍是 RR。RRTR 只是给 RR 补的钟。

## 3. 核心辨析三: 两个 SSRC 各司其职(本对话最大的澄清点)

DLRR 包里出现两个不同的 SSRC, 别混:

| 位置 | 含义 | SFU 回 DLRR 时的值(推流端视角) |
|------|------|------|
| XR **头** SSRC | 这个包是谁发的(packet sender) | 推流端自己的媒体 ssrc(如 2845xxxx) |
| DLRR **子块** ssrc | 这个报告**关于谁** | SFU 的号 = 1(kDefaultVideoSsrc) |

代码印证: `HandleXrDlrrReport` 过滤用的是 `rti.ssrc`(子块的 1), 而**不是** `xr.sender_ssrc()`(推流端的号)——我们要的是"关于我们"的报告, 头 SSRC 只告诉我们包从哪来。

## 4. 为什么协议和实现最终收敛(复合包视角)

A 发的复合包是 `[RR(201) sender=1] + [XR(207) sender=1, BT=RRTR]`, 两个块**同一个 sender ssrc**:

- 协议视角: DLRR 报告 "我收到过谁的 RR" → ssrc = 1
- 实现视角: DLRR 子块 ssrc = 从 RRTR 头抄的号 = 1

两条路收敛到同一个号。严格说 "同一复合包" 不是 DLRR 关联 RR 的原因(RFC 定义本来就关联), 但复合包同 sender 让两个视角完全重合。

## 5. 完整链路(SFU ↔ 推流端, v11.x/12.1 的 XR 是上行链路)

```
SFU(接收侧):  发 RR + XR(RRTR), 头 SSRC = 1(local_media_ssrc = kDefaultVideoSsrc)
        ↓
推流端:       libwebrtc 存下 (1, RRTR 的 NTP)
        ↓
推流端:       回 XR(DLRR): 头 SSRC = 推流端自己的媒体号
              子块{ ssrc = 1, last_rr = RRTR 的 NTP, delay = 距上次报告时长 }
        ↓
SFU:          HandleXrDlrrReport(rti.ssrc == 1)
              → register_ssrcs_.Contains(1) 命中
              → RTT = now − last_rr − delay
              → xr_rr_rtt_ms_ = CompactNtpRttToMs(rtt_ntp)
              → OnRttUpdate(xr_rr_rtt_ms_)
```

## 6. register_ssrcs_ 设计

```cpp
RegisteredSsrcs(const RtpRtcpConfig& config) {
    ssrcs_.push_back(config.local_media_ssrc);   // 必收: 媒体号 = 1
    if (config.rtx_send_ssrc > 0) {
        ssrcs_.push_back(config.rtx_send_ssrc);  // 防御性条目
    }
}
```

- 过滤顺序: **先 `Contains(rti.ssrc)` 再 `enable_xr_`**(与参考 v12.1 一致)
- rtx 条目是**防御性的**: 标准 libwebrtc 回 DLRR 永远写媒体 ssrc——RTCP 一律用媒体号发(RFC 4588 规定 RTX 通道只走 RTP 不走 RTCP), 实际只会命中媒体号
- 子块 ssrc 永远是 "对方从我发的 RRTR 头里抄的号" = 本端媒体 ssrc = 1
