### Phase 4 — RTP 广播分发（7.7 ~ 7.8）

## 拓展 — mediasoup 核心模型 vs 手写 xrtc-server 逐项对照（入职绿联前准备）

> 背景：绿联 SFU 基于 **mediasoup**（媒体引擎）+ **Golang**（上层控制/信令）。入职前把 mediasoup 核心模型与手写 xrtc-server 逐项对照，用已有的 SFU 深度快速迁移理解。
> 核心思想：xrtc-server 里写过的每个概念，mediasoup 都有对应物——对照着学，比从零学快得多。

### 对照映射表（学习路线）

| xrtc-server（手写） | mediasoup | 对照要点 |
|--------------------|-----------|---------|
| RtcServer / RtcWorker | **Worker**（C++ 子进程，每 worker 占一核） | 媒体处理进程，对应你的 worker 线程模型 |
| RtcStreamManager | **Router** | 一组媒体连接的管理单元（按 room/流） |
| PeerConnection / TransportController | **WebRtcTransport**（ICE/DTLS/SRTP） | 传输层，你全写过 |
| PushStream / VideoReceiveStream | **Producer** | 推流侧（接收对端媒体） |
| PullStream / VideoSendStream | **Consumer** | 拉流侧（发给对端） |
| RtcPacket 缓存 + FindVideoPacket（2048 槽位） | Consumer 的 RTP 缓存/重传 | 下行 NACK/重传的对应物 |
| OnRtpPacket 广播（1V多） | Router 多 Consumer 扇出 / PipeTransport | 一推多拉的 mediasoup 形态 |
| RTCP 处理（SR/RR/NACK/REMB） | **RtpObserver**（BandwidthEstimator） | 带宽估计/码率控制的 mediasoup 位置 |
| 信令（signaling Go） | **Go 控制面**（mediasoup API + worker 通信） | 入职后要写的 Go 层 |

### 学习步骤

1. **mediasoup 架构**：Worker → Router → WebRtcTransport → Producer/Consumer → RtpObserver 这套模型；RTP 转发、RTCP 处理、带宽估计怎么跑
2. **对照迁移**：用上面映射表，把 xrtc-server 里写过的每个模块，在 mediasoup 源码里找到对应实现
3. **Go 上层**：语法基础 → goroutine/channel → Gin/Echo → 控制面（mediasoup API + worker socket 通信）
4. **1V多 对照**：重点看 mediasoup 怎么把 1 个 Producer 扇出到多个 Consumer（对应你的 multi_pull_streams_ 广播）

### 为什么值得做

- 面试官明确让研究 mediasoup + golang → 这是入职前功课
- 你是少数"从零写过 SFU"的人 → 理解 mediasoup 内核时是 protocol 级，不是 API 级
- 深度（SFU 内核）+ 生态（mediasoup）+ Go 控制面 = 更值钱的组合

## 拓展二 — VideoControl 客户端对接 mediasoup 改造计划

> 目标：把自研客户端（Electron + SDK/libwebrtc，SDP offer/answer 模型）接到自部署的 mediasoup 上，用"信令桥"方案，**客户端改动≈0**。
> 背景：客户端信令模型是"**服务器出 offer、客户端回 answer**"；mediasoup 是"**客户端交 ICE/DTLS 参数 → 服务端返回 → produce/consume**"。信令桥负责翻译两者。

### 架构

```
VideoControl 客户端 (libwebrtc, offer/answer)
   │  pull/push 请求 + answer
   ▼
Node.js 信令桥 ──►  mediasoup (Worker/Router/Transport/Producer/Consumer)
   │  生成 SDP offer(mediasoup 参数) / 解析客户端 answer / codec 对齐
   ▼
云服务器 (公网 IP + RTC 端口)
```

### 实施步骤

**Step 0 — 部署 mediasoup**（半天~1天）
- 云服务器 `npm install mediasoup ws`
- 最小 server：createWorker → Router → 暴露信令接口
- 关键：WebRtcTransport 配公网 IP（announcedIp）+ RTC 端口区间 + 防火墙放行

**Step 1 — 浏览器验证**（隔离变量）
- 官方 mediasoup-client demo（HTML+JS）连上去推/拉一路
- 验证：服务器部署对、ICE/DTLS 穿透通、网络路径 OK

**Step 2 — 写信令桥**（核心，几百行 Node.js）
- 桥要做三件事：
  1. **生成 SDP offer**：把 mediasoup transport 的 ICE ufrag/pwd + DTLS fingerprint + Router codec（H.264 PT/profile-level-id/RTX）编成 SDP（可用 `sdp-transform` 库）
  2. **解析客户端 answer**：抽客户端的 ICE ufrag/pwd + DTLS fingerprint → `transport.connect()`
  3. **codec 对齐**：Router 的 RTP capabilities 必须包含客户端用的 codec，PT 对上
- DTLS role：桥生成的 offer 方向决定 mediasoup 是 server 还是 client 角色，选对

**Step 3 — 接客户端**
- VideoControl `main.js` 改 `signalingBase` 指向桥（客户端代码改动≈0）
- 跑通推/拉流

**Step 4 — 对照验证**（1V多 + 与 xrtc-server 对照）
- 1 推 + 2 拉过 mediasoup：验证多 Consumer 扇出（对应你的 multi_pull_streams_ 广播）
- 对照 xrtc-server：Producer/Consumer ↔ PushStream/PullStream 的行为差异
- 下行码率：对比 mediasoup 的带宽估计 vs 你的 REMB 思路

### 关键坑

1. 公网 IP / ICE candidate：云服务器必须广告公网 IP，否则客户端连不进
2. 端口：RTC 端口区间要在防火墙放行
3. DTLS-SRTP：mediasoup 强制加密，libwebrtc 客户端天生支持（无明文回退）
4. DTLS role：offer 方向决定 mediasoup 是 server 还是 client
5. codec PT：H.264 profile-level-id 必须和 Router capabilities 匹配

### 验收清单

- [ ] 浏览器连 mediasoup 推/拉成功（Step 1）
- [ ] VideoControl 客户端过信令桥连 mediasoup 推/拉成功（Step 3）
- [ ] 1 推 2 拉：两个拉流端都能出画（Step 4）
- [ ] 对照结论：能说出 mediasoup 与自研 SFU 在信令模型/转发结构上的差异
