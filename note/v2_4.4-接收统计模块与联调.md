# v2_4.4 接收统计模块（ReceiveStat）

> 对应参考课程：`xrtc2.0-9.9/xrtcserver_v2_4.4`
> 本次改动：新增 `ReceiveStat` 接收统计模块，接入 RTP 到达链路打日志验证
> 联调结论：推流 SSRC 与 answer 一致、sequence_number 连续递增，链路闭合

## 一、本节课解决的问题

4.3 打通了 `PeerConnection::OnRtpPacketReceived`（解析 RTP 头 + 按 SSRC 分拣 + 投递到 VideoReceiveStream），但接收到的包**没有消费**——只有链路，没有数据积累。

4.4 引入 `ReceiveStat`：为后续 RTCP RR（Receiver Report）准备**数据源**。每次收到 RTP 包累计原始数据（SSRC/序列号/到达时间），后续课程（4.10）在此基础上生成 RR 的 report blocks。当前课程只建容器 + 打日志验证链路。

## 二、核心代码结构

```
src/modules/rtp_rtcp/receive_stat.{h,cpp}  新增
  └─ ReceiveStat
       ├─ Create(clock)          工厂方法
       └─ OnRtpPacket(packet)    每包累计（当前打日志）
```

接线改动（4 个文件）：
- `video/video_receive_stream.{h,cpp}`：持有 `std::unique_ptr<ReceiveStat>`（**唯一拥有者**）
- `video/rtp_video_stream_receiver.{h,cpp}`：构造接收 `ReceiveStat*`（**裸指针借用**），`OnRtpPacket` 里 `if (!packet.recovered())` 排除重传包后喂给统计

**所有权关系**（初始化列表顺序 = 声明顺序）：

```cpp
// VideoReceiveStream 构造函数
config_(config),
rtp_receive_stat_(ReceiveStat::Create(config.clock)),      // ① 先创建统计模块
rtp_video_stream_receiver_(config, rtp_receive_stat_.get()) // ② 把裸指针借给接收器
```

## 三、消息流程

```
ICE channel 收到推流 RTP 包
  → TransportController::SignalRtpPacketReceived
  → PeerConnection::OnRtpPacketReceived          (4.3)
  → RtpPacketReceived::Parse(move(buffer))        解析头部字段
  → set_arrival_time()                            记录到达时间（jitter 基准）
  → GetMediaType(ssrc): remote_video_ssrc_/rtx → VIDEO
  → VideoReceiveStream::OnRtpPacket
  → RtpVideoStreamReceiver::OnRtpPacket
  → !packet.recovered()                           排除 RTX 重传恢复的包
  → ReceiveStat::OnRtpPacket                      打日志（验证点）
```

## 四、两个关键设计点

### 1. 为什么排除 `recovered()` 的包

`recovered()` = 由 RTX/重传恢复出的包。接收统计（丢包率/jitter）只应反映**真实到达**的包，若把重传恢复的包计入，会歪曲丢包率计算（看起来没丢，其实是丢了又补）。

### 2. 裸指针借用 vs unique_ptr 拥有

- `VideoReceiveStream` 用 `unique_ptr` 持有统计模块——**生命周期管理方**
- `RtpVideoStreamReceiver` 只拿裸指针——**只喂数据，不负责释放**
- 借用指针比直接持有统计对象更合理：接收器只依赖接口，所有权集中在流对象

SDP answer 视频主 SSRC `176075053`（`ssrc-group:FID 176075053 2603122861`），SFU 日志：

```

WARNING: ... receive_stat.cpp:25: ====================ssrc: 176075053, sequence_number: 2718
WARNING: ... receive_stat.cpp:25: ====================ssrc: 176075053, sequence_number: 2719
```

- ✅ SSRC 与 answer 完全一致 → `CreateVideoReceiveStream` 正确记录 `remote_video_ssrc_`
- ✅ sequence_number 连续递增、无跳号 → 真实持续 RTP 流，不是偶发包
- ⚠️ 日志只有视频 SSRC、没有音频——**符合预期**：`GetMediaType` 音频 SSRC 返回 AUDIO，`OnRtpPacketReceived` 只处理 VIDEO 分支（音频接收链路后续课程才有）

## 六、联调踩坑记录（重要）

### 坑 1：`SignalRtpPacketReceived` 屏蔽 → 新旧代码联调表现差异

4.3 把 `PeerConnection::OnRtpPacketReceived` 里原本的转发语句注释了：

```cpp
// 4.3 之前：
SignalRtpPacketReceived(this, packet, ts);   // 转发给上层（RtcStream）
// 4.3 之后：
//SignalRtpPacketReceived(this, packet, ts);  // 改为只解析 + 统计
```

而 **`RtcStream`（PushStream 基类）全靠这个信号收 RTP**（`rtc_stream.cpp:34` connect → `OnRtpPacketReceived` → `listener_`）。注释后 **PushStream 断粮，拉流不再有画面**。

**联调排查的价值**：当时云机跑旧代码，现象是"拉流有画面 + 无统计日志"——恰好是**旧代码**的行为签名（信号还发射 → 画面有；无统计逻辑 → 无日志）。而新代码下应该是"有统计日志 + 无转发画面"。**看到"有画面无日志"，第一反应就是云机代码没同步/没重编。**

### 坑 2：`sync_cloud.sh` 不同步 CMakeLists.txt → 云机漏编

云机编译 `undefined reference to VideoReceiveStream`。原因：CMakeLists 用 `file(GLOB)` 收源文件，但 `sync_cloud.sh` 只同步 `src/` 和 `conf/`，**没同步 CMakeLists.txt**——云机停留在没有 `./src/video/*.cpp` 的旧构建配置，video 目录整个没进编译。

修复：`sync_cloud.sh` 补上 CMakeLists.txt 同步。**凡是 CMakeLists 新增目录 GLOB，同步脚本必须带上 CMakeLists 本身。**

## 七、与 RTCP RR 的关系（后续课程）

- 4.4 只建数据源容器：`ReceiveStat::OnRtpPacket` 累计原始数据
- RR 格式到 4.10 才出现：`receive_stat_->RtcpReportBlocks(RTCP_MAX_REPORT_BLOCKS)` 生成 report blocks
- 时间线：4.3 解析 RTP → 4.4 统计容器 → 4.5+ StreamStat 按 SSRC 分流 → 4.10 RR 生成
