# v2_4.7 乱序/序列突变检测与累计丢包账本模型

> 对应课程：`xrtcserver_v2_4.7`
> 状态：**已解决**（2026-08-11 讨论闭环，代码 351ba37 与参考逐行一致）
> 核心问题：为什么突变确认时 `received_seq_max_ = sequence_number - 2`，而不是 -1？为什么突变后 loss 是 1 不是 0？
> 代码位置：`src/modules/rtp_rtcp/receive_stat.cpp` `StreamStat::UpdateCounters` / `UpdateOutOfOrder`

## 一、账本模型的数学本质

`cumulative_loss_` 维护的目标 = **期望收到的包数 − 实际收到的包数**（累计丢包）。

两条增量规则（缺一不可）：

```
每个包到达：       --cumulative_loss_    （实际收到 +1 → 丢失 -1，"还自己到货的账"）
顺序新包推进：     += (seq − max)        （前沿推进到 seq，期望收到数 + 缺口）
```

顺序路径的实际代码（含无条件提前的 `-1`）：

```cpp
--cumulative_loss_;                                      // ① 每包无条件 -1
...
cumulative_loss_ += (sequence_number - received_seq_max_); // ② 顺序补差
received_seq_max_ = sequence_number;
```

## 二、三条路径逐个推演

### 1. 顺序（seq > max）——理想状态

新包 `seq` 与 `max` 之间缺 `(seq − max − 1)` 个，但①已提前 `-1`（还自己到货的账），
所以②要 `+= (seq − max)` 把"自己那份"补上 → 净效果 `(seq − max) − 1` = 真正新增缺失。

验证：`max=3, seq=5`（缺 4）→ `-1 + 2 = +1` ✓

### 2. 乱序（seq < max）——只撤销自己的账

`1 2 3 8` 时，收到 8 的补差 `(8−3)=5` 已把 4/5/6/7 的缺失全记账。再收到 `6`：
- 6 之前被计为缺失，现在到货，只需①的 `-1` 撤销它自己那笔
- **必须短路 return**：不能执行②补差、不能更新 max（否则重复计数）

### 3. 突变（|seq − max| > 450）——两步确认

```cpp
// ② 怀疑：与前沿差超阈值
if (abs(sequence_number - received_seq_max_) > max_reordering_threshold_) {
    received_seq_out_of_order_ = packet.SequenceNumber();  // 记下突变包的原始 seq
    ++cumulative_loss_;                                    // 触发包先计 1 丢
    return true;                                           // 短路，不更新前沿
}

// ③ 确认：下一包 == 突变包 + 1
if (received_seq_out_of_order_) {
    if (packet.SequenceNumber() == expected_seq_num) {
        received_seq_max_ = sequence_number - 2;   // ★ 核心：max 比确认包低 2
        return false;                              // 走顺序路径
    }
}
```

## 三、-2 的完整账目推演（前沿 100、账 0，来 600/601/602）

| 包 | ① 提前-1 | 突变处理 | ② 补差 | 账 | 说明 |
|----|:---:|------|:---:|:---:|------|
| **600** | -1 | 怀疑 `++`(计丢) | — | **0** | 短路 return，max 不动 |
| **601** | -1 | 确认 `max = 601−2 = 599` | `+2` | **+1** | 走顺序路径 |
| **602** | -1 | — | `+1` | **1** | 顺序，稳态锁定 1 |

**稳态：账恒 = 1**（后续每包 `-1 +1` 抵消，不放大）。

### -2 vs -1，差一个"触发包算丢还是算收"

| 设定 | 确认包净账 | 触发包 600 的账目 | 稳态 |
|------|:---:|:---:|:---:|
| `max = seq − 1` | `-1 + 1 = 0` | 收到 | **0** |
| `max = seq − 2` | `-1 + 2 = +1` | **丢失** | **1** |

所以 `-2` 的语义精确为：**突变确认后，触发包在账本里算 1 笔丢失**。

## 四、为什么是 1 不是 0（核心问题）

直觉：`1 2 3 500 501` 是新流，500 501 没丢，loss 该是 0。

但同一个 seq 序列，两种解释都成立，**协议层无法区分**：

| | 解释 A（流切换） | 解释 B（同流丢大段） |
|---|---|---|
| 场景 | 旧流 1 2 3 结束，新流 500 起 | 同一流，4~499 全被网络丢 |
| 真实丢失 | 0 | 496 |
| seq 表现 | 1 2 3 500 501 | 1 2 3 500 501（一模一样）|

### 突变检测是"防爆器"，不是"清零器"

没有突变检测，500 按顺序路径会 `补差 (500−3) = 497` → **loss 直接爆炸**。
无论 A/B，497 都不对（A 假丢，B 多 1）。

### 三种策略的取舍

| 策略 | 解释 A（真切换）| 解释 B（真丢断）|
|------|:---:|:---:|
| 清零（=0） | ✅ 对 | ❌ 低估 496 |
| 全计（=496）| ❌ 高估 496 | ✅ 对 |
| **记 1 丢** | 高估 1（可接受）| 低估 495（可接受）|

**WebRTC 的拥塞控制哲学：丢包率是拥塞控制输入，宁可高估、不可低估。**
低估丢包 = 假装网络很好 = 拥塞不收敛。所以突变边界保守记 1 丢，绝不清零。

## 五、换 SSRC = 新桶 = 天然清零

真正意义上的"流切换"会被**自动清零**——因为它会换 SSRC：

```
推流方换新流 → 新 SSRC → GetOrCreateStat 新建统计桶 → 新桶 loss 从 0 开始
```

所以"该清零"的直觉，在换 SSRC 的真切换里已经实现（新桶天然清零）。

而突变检测面对的场景恰恰是：**SSRC 没变、seq 却断**——要么同流丢大段（B），要么流重置复用 SSRC（A 变体）。这是最模糊的地带，WebRTC 不赌，记 1 丢作为"连续性断裂"的保守标记。

## 六、结论

> **每包先还一账（-1），顺序新包把缺口补全（+seq−max），乱序只撤自己那账；突变边界保守记 1 丢——不是代码不会清零，是它不敢（分不清换流/丢断）；而换流清零的活，已由"换 SSRC = 新统计桶"干掉了。**

### 三个常见疑问速答

1. **为什么 -2 不是 -1？** → 数学效果是"触发包计 1 丢 vs 计收"；参考选择计丢（保守防低估）。
2. **-2 的账怎么对平？** → 触发包 `-1+1=0`，确认包 `-1+2=+1`，合计 **+1 = 触发包 600 算 1 丢**。
3. **突变后触发包算丢还是收？** → **丢**（-2 的语义），且稳态恒定不放大。
