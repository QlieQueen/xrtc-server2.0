# v2_12.1 NACK 重传间隔 = RTT(1500ms 窗口取最大值)

> 配套代码:v2_11.2~11.5(XR RRTR/DLRR 链路,本课接通消费端)+ 本课(PeerConnection 窗口取最大 → NackRequester)。
> 参考实现:参考仓库 v12.1(bbc38e9)。

## 0. 要解决的问题

**如何合理设置 NACK 的重传间隔?** 即:发了一次 NACK 请求重传,如果重传包又丢了(或还没到),隔多久再发一次请求?

## 1. 为什么间隔 = RTT 是最优点

从发送 NACK 到发送端,再到重传数据抵达接收端,**至少需要一个 RTT 的时间**。所以:

- **间隔太长** → 数据一直在等,重传迟迟不来,引起较大延迟
- **间隔太短** → 重传包还在路上(尚未到达),又发一次 NACK——大量**无效重传**(重传是需要时间的,必须预留这段时间给它)
- **间隔 = RTT** → 既给重传数据预留了充分的传输时间,又避免了大量无效重传——**最优**

## 2. WebRTC 的做法:1500ms 窗口取 RTT 最大值

RTT 是**波动的**(网络状况实时变化),单次实测值可能偏小(碰巧网络好)。如果直接用"当前最新值"做间隔,某次抖动让 RTT 瞬时回落,间隔会跟着缩,又回到"无效重传"的老路。

所以 WebRTC 取**一段时间(1500ms)内的 RTT 最大值**设置到 Nack 模块——宁可保守(间隔偏大一点),也不让间隔被瞬时低值带偏。**宁大勿小**。

> 生活类比:等人约好"到齐就出发",但如果有人迟到了,你会按"这段时间里最慢那个人"的标准等,而不是按最快那次的标准——NACK 间隔同理,按窗口内最坏情况(RTT 最大)来。

## 3. 本工程实现链(SFU↔推流端 上行 NACK)

```
推流端 XR(DLRR 子块)
  → RTCPReceiver::HandleXrDlrrReport 算单次 RTT        (v2_11.4)
  → OnRttUpdate(xr_rr_rtt_ms_)                          (rtcp_receiver.cpp)
  → PeerConnection::OnRttUpdate                          (v2_12.1, 本课)
      ├─ rtt_reports_.push_back(RttTime(now, rtt_ms))   // 收集样本
      ├─ RemoveOldReport: 丢 1500ms 前的旧样本
      └─ GetMaxRttTimeMs: 取窗口内最大值
  → VideoReceiveStream::OnRttUpdate(max)
  → RtpVideoStreamReceiver::UpdateRtt(max)
  → NackRequester::UpdateRtt(max)  → rtt_ms_
  → ProcessNacks(): 重传过的包按 rtt_ms_ 退避再次点名   (v2_6.x 已实现, 当时默认 100ms)
```

关键点:

- **6.x 已实现退避逻辑**,但 `rtt_ms_` 一直是默认值 `kDefaultRttMs = 100ms`(无实测 RTT)。本课把 XR 实测 RTT 接进来,重传间隔从"拍脑袋 100ms"变成"实测最优"
- 窗口在 **PeerConnection** 层做(不在 rtcp_receiver):因为 rtcp_receiver 只负责算单次值,策略层(取最大/过滤)留给 PC——职责分离
- 上报链走 `rtp_rtcp_module_observer_`(Observer 模式),PC 实现了该接口

## 4. 联调验证(云端 1 推 1 拉)

```
rtt_ms: 49    →  nack rtt: 49     // 窗口内只有本次样本, 最大=本次
rtt_ms: 54    →  nack rtt: 54     // 同上
rtt_ms: 40    →  nack rtt: 54     // 本次实测 40 < 窗口内最大 54 → 下发 54
```

第三行是精髓:**RTT 瞬时降到 40,NACK 间隔不跟着缩,保持 54**——1500ms 窗口取最大真实生效,防住了"无效重传"。

## 5. 踩坑:UpdateRtt 的日志打印顺序

联调时看到 `rtt_ms: 63` 而 `nack rtt: 56`,以为链路传错值。实际是:

```cpp
// ❌ 打印在赋值前 → 显示的是上一次喂入的旧值
RTC_LOG(...) << rtt_ms_;   // 56 (旧值)
rtt_ms_ = rtt_ms;           // 本次才赋值

// ✅ 先赋值后打印(与参考 v12.1 一致)
rtt_ms_ = rtt_ms;
RTC_LOG(...) << rtt_ms_;   // 63 (本次值)
```

**教训:打印调试日志要"先赋值后打印",否则排查时永远看到滞后一个周期的值。**
