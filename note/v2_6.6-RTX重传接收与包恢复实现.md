## 二、恢复实现（对照 6.4 蓝图）

```cpp
void RtxReceiveStream::OnRtpPacket(const webrtc::RtpPacketReceived& rtx_packet) {
    // 统计 RTX 原包（独立 RTX 流桶，见三）
    if (rtp_receive_stat_) {
        rtp_receive_stat_->OnRtpPacket(rtx_packet);
    }

    // ① 校验: RTX 包至少带 2 字节 OSN
    rtc::ArrayView<const uint8_t> payload = rtx_packet.payload();
    if (payload.size() < webrtc::kRtxHeaderSize) {
        return;
    }

    // ② 识别: 查 rtx_PT → 媒体_PT 映射, 查不到 = 不是认识的 RTX 通道
    auto it = rtx_associated_payload_types_.find(rtx_packet.PayloadType());
    if (it == rtx_associated_payload_types_.end()) {
        RTC_LOG(LS_WARNING) << "unknown payload type: " << ...;
        return;
    }

    // ③ 构造恢复包: 拷 RTP 头(timestamp/M 保留) + 还原三样
    webrtc::RtpPacketReceived media_packet;
    media_packet.CopyHeaderFrom(rtx_packet);
    media_packet.SetSsrc(media_ssrc_);                    // SSRC ← 原媒体 SSRC
    media_packet.SetSequenceNumber((payload[0] << 8) + payload[1]); // seq ← OSN(大端)
    media_packet.SetPayloadType(it->second);              // PT ← 原媒体 PT
    media_packet.set_recovered(true);                     // 标记: 这是恢复出来的包
    media_packet.set_arrival_time(rtx_packet.arrival_time()); // 到达时间必须带上

    // ④ 去 OSN: payload 跳过前 2 字节, 拷贝剩下的媒体数据
    rtc::ArrayView<const uint8_t> rtx_payload = payload.subview(webrtc::kRtxHeaderSize);
    uint8_t* media_payload = media_packet.AllocatePayload(rtx_payload.size());
    memcpy(media_payload, rtx_payload.data(), rtx_payload.size());

    RTC_LOG(LS_WARNING) << "=============recover packet seq: " << media_packet.SequenceNumber();

    // ⑤ 喂回媒体接收端, 走正常组帧/统计/记账链路
    media_sink_->OnRtpPacket(media_packet);
}
```

注意 `set_arrival_time`：恢复包不带上到达时间会破坏 PacketBuffer 的乱序排序和 jitter 采样，必须从 RTX 包拷过来。

## 三、统计分工（为什么开头喂 RTX 原包）

`ReceiveStat` 按 SSRC 建桶，形成**双桶分离**：

```
媒体流桶 (SSRC = media_ssrc)
  主接收流收媒体包 → 统计            ← 首达丢包率
  恢复包进来 → RtpVideoStreamReceiver 里 !recovered 排除   ← 不进媒体桶

RTX 流桶 (SSRC = rtx_ssrc)
  RtxReceiveStream 开头喂 RTX 原包 → 统计   ← 反映重传通道质量
```

- RTX 原包 SSRC=rtx_ssrc，`GetOrCreateStat` 单独建桶，统计的是重传通道自己（RTX 流独立 seq 序列、自身有没有丢包）
- 恢复包 `recovered=true` 喂回 `media_sink_` 后，被 `RtpVideoStreamReceiver::OnRtpPacket` 的 `if (!packet.recovered())` 挡住 → 不重复统计
- 两个桶各管各的，RR 报告里多出的 rtx_ssrc 报告块 = 报给推流端"重传通道质量"

## 四、联调验证（NACK 点名 vs recover 一一对应）

grep `nack packet ids`（发出点名）与 `recover packet seq`（恢复成功）两份日志对齐：

| NACK 点名 | recover | 时延 |
|---|---|---|
| [032:749] 30403 | [032:759] 30403 | 10ms |
| [032:946] 30416 | [032:960] 30416 | 14ms |
| [034:847] 30529 | [034:861] 30529 | 14ms |
| [043:126] 30832 | [043:137] 30832 | 11ms |

**结论：53 个点名包，53 个全部恢复，无遗漏。**

三个看点：

1. **时延 10~14ms = 网络 RTT**：NACK 发出 → 客户端 RTX 重传 → 服务端恢复，一个往返。正是 6.1 `UpdateRtt` 想喂的实测值。
2. **重复点名 = NACK 重试退避**（30608/30699/30806）：第一次点名后重传没到（RTX 通道自己丢一次），NackRequester 按退避间隔（~119ms）再点，第二次补上。
3. **一次点名两包、重传乱序到达**（30699+30700）：各自读 OSN 还原成正确媒体 seq，互不干扰。

另外，`parsing rtp payload failed` 噪声彻底消失——RTX 包不再被当普通 H264 乱解析（6.3 现象消除）。

## 五、恢复包在 NackRequester 的路径（销账）

恢复包喂回主链 → `OnReceivedPayloadData` → `nack_module_->OnReceivedPacket(seq, ...)`：

```
恢复包 seq 比 newest_seq_num_ 旧（它丢过）
  → AheadOf(newest, seq) == true → 旧包分支
    → 查 nack_list_.find(seq)
      → 在档 → retransmission received 日志 + erase 销账  ← 剔除, 不再重复点名
      → 不在档 → 纯乱序, 返回 0
```

这段销账**不受第三个参数影响**，永远执行——它就是恢复包"被补上"的账本登记。

## 六、遗留与后续（记录在案）

1. **调用点第三个参数**：当前 `OnReceivedPacket(seq, is_keyframe, false)` 写死 false，导致恢复包也被当真乱序统计进 `reordering_histogram_`（污染 NACK 等待线）。计划改为 `rtp_packet.recovered()`，让恢复包 `is_retransmitted=true` 跳过乱序统计。**单独 commit 处理。**
2. **`recovered_list_`（6.1 遗留，参考有、本实现未做）**：参考 OnReceivedPacket 有 `if (is_recovered)` 分支记入 `recovered_list_`，`AddPacketsToNack` 点名缺口时跳过已恢复的包（防重复点名）。本实现靠 nack_list_ 销账已覆盖此作用，暂不实现，备忘。

## 七、一句话记忆

> **6.6 = RTX 恢复闭环打通**：`OnRtpPacket` 读 OSN 还原 seq/PT/SSRC、去 OSN、标 recovered、带上到达时间，喂回主链；统计走**双桶**（RTX 原包独立桶反映重传通道，恢复包被 `!recovered` 挡在媒体桶外）。验证：**点名 53 恢复 53，一一对应，RTT ≈ 10ms**——NACK → RTX 重传 → 恢复，丢一个补一个。
