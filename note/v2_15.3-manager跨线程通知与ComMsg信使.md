# v2_15.3 manager 跨线程通知基础设施（pipe 门铃 + ComMsg 信箱）

> 配套代码：v2_15.2（拉流按 uid 哈希打散到多 worker）+ 本课（manager 自建 pipe/Notify/ComMsg，**未接线**）。
> 参考实现：参考仓库 v15.3（71ce56e）。`Init()` 要到 v15.4 才被 rtc_worker 调用。

## 0. 要解决的问题

15.2 之后，pull 落在 worker B、push 在 worker A——B 的 manager 想查/订阅 A 的推流，**不能直接跨线程调**（数据竞争），必须异步投递。本课给每个 RtcStreamManager 装上自己的跨线程唤醒三件套，为 15.4+ 的订阅链铺路。纯基础设施：写完编译通过，运行时无任何行为变化。

## 1. 三件套套路（本工程第三次出现）

| 部件 | 角色 | 本课对应 |
|----|----|----|
| 队列 | **信箱**：装真正的消息（大对象） | `mq_msg_`（LockFreeQueue\<shared_ptr\<ComMsg\>\>） |
| pipe | **门铃**：只过 4 字节 int，唤醒 event loop | `notify_send_fd_` / `notify_recv_fd_` |
| 回调 | **消费**：宿主线程被唤醒后处理 | `RtcStreamManagerRecvNotify` → `ProcessNotify` |

与 RtcWorker / SignalingWorker 完全同款。两个设计要点：

- **门铃必须小**：定长 4 字节写入原子、配 O_NONBLOCK 后永不阻塞发送方
- **信箱不能省**：epoll 只能盯 fd，消息本体（shared_ptr 大对象）没法塞进 pipe；pipe 只负责"有事"，队列负责"是什么事"

## 2. 四个部件

### ComMsg（信件，manager 间跑的消息）

```cpp
struct ComMsg {
    int msg_type = -1;                        // 消息类型（15.4+ 定义枚举）
    int worker_id = -1;                       // 回信地址：发起方是哪个 worker
    uint64_t uid = 0;
    std::string stream_name;
    std::vector<StreamParams> audio_source;   // 推流端媒体源（ssrc 等）
    std::vector<StreamParams> video_source;
};
```

拉流 worker 手里没有推流信息，`audio/video_source` 负责把推流端的 StreamParams 带过去。`worker_id` 是回信地址——对端处理完要知道回哪里。

### Init()（消费端注册）

pipe + send 端 O_NONBLOCK + `el_->CreateIOEvent/StartIOEvent` 监听 recv fd。关键认知：**`el_` 是宿主 worker 的事件循环，回调永远在本 manager 的宿主线程执行**——"消息最终回到自己线程处理"的保证。

### Notify(int type)（生产端门铃）

**由别的线程调用**：往 send fd 写一个 int。

### ProcessNotify(int type)

空壳，15.4+ 填肉（drain `mq_msg_` 并分发）。

## 3. 本课两个讨论（面试点）

### 3.1 lock-free 队列为什么还要配 mutex

看实现（`lock_free_queue.h`，Sutter 式 divider 队列）：注释明写"一个生产者，一个消费者"。`Produce` 的 `last->next = new Node(t); last = last->next;` 是**两步非原子**操作，两个生产者并发会互相覆盖 `next`、丢节点。

工程内现成对照：`RtcWorker::q_msg_` **裸用无锁**（rtc_worker.cpp PopMsg 直接 Consume）——它的生产者只有 RtcServer 线程一个，天然 1P1C，免锁前提成立。而 `mq_msg_` 的生产者是**任意其他 worker 线程**（N 个拉流 worker 都可能给同一个推流 manager 投 ComMsg）：N 生产者 + 1 消费者 → 外加 `mq_msg_mutex_` 把 N 个生产者串行化，人为恢复"同一时刻至多一个生产者"。

**一句话：lock-free 免锁的资格恰恰来自 1P1C，多生产者就得外面自己补锁。**

### 3.2 为什么只给 send fd 设 O_NONBLOCK

- 一个门铃 4 字节，pipe 默认缓冲 64KB，要积压 **16000+** 个未读通知才会满。正常消费者一唤醒就读，积不起来——**写满 ≈ 消费者线程已死/卡死**，是异常态而非"读得慢"
- 不设的后果是**级联故障**：写方（某拉流 worker 的 event loop）阻塞在 `write()` → 该 worker 上所有流停摆 → 一个 worker 的故障传染给另一个
- 设了之后 `write` 返回 -1，记 warning 丢门铃，**故障隔离在收端**
- recv fd 不用设：回调是 READ 事件触发后才读 4 字节，level-trigger 保证有数据才进来

**铁律：跨线程通知通道，发送方永远不能被接收方拖死。**

## 5. 面试表达主线

> "多个 worker 之后线程间协作全要异步化。我们的方案和 WebRTC 里线程间消息一个套路：一个 lock-free 队列装消息本体，一个 pipe 当门铃——epoll 只能等 fd，所以用 4 字节写入做原子唤醒，消息走队列。有个细节是这个队列免锁的前提是单生产者单消费者，而 manager 的队列是 N 个 worker 都会投递，所以外面又包了一把 mutex 把生产者串行化。另外 pipe 发送端设非阻塞，写满说明对端线程已经异常，宁可丢通知也不能把发送方 worker 阻塞住——跨线程通道不能让发送方被接收方拖死。"
