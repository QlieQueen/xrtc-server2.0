# v2_4.2 VideoReceiveStream 创建 + SDP 协商格式讨论（PlanB / UnifiedPlan）

> 对应参考课程：`xrtc2.0-9.9/xrtcserver_v2_4.2`
> 本次改动：`SetRemoteSdp` 解析完 answer 后创建 `VideoReceiveStream`（取第一条视频流的第一个 SSRC）
> 本文同时记录一次完整讨论：WebRTC 原生 `VideoTrack` 在 SDP 里的表现形式、PlanB 与 kUnifiedPlan 两种格式的差异、answer 镜像 offer 原则，以及——**我们为什么敢用 PlanB 的方式解析 SDP，不怕原生客户端用 UnifiedPlan 的 SDP 来协商**。

## 一、本节课解决的问题

v2_4.1 只创建了 `VideoReceiveStream` 的骨架（类定义 + 空实现），但没有任何地方实例化它。本节课在 `SetRemoteSdp` 里把它真正接上：answer 解析出视频 SSRC 后，创建接收流，后续 RTP 才会被投递到接收流处理。

```cpp
// peer_connection.cpp — SetRemoteSdp 末尾
remote_desc_->AddTransportInfo(audio_td);
remote_desc_->AddTransportInfo(video_td);

CreateVideoReceiveStream(video_content.get());   // ← 本节课新增

transport_controller_->SetRemoteDescription(remote_desc_.get());
```

```cpp
void PeerConnection::CreateVideoReceiveStream(VideoContentDescription* video_content) {
    // 按照系统的推拉流原子设计原则，一个 peerconnection 只允许推一个或者拉一个视频
    for (auto send_stream : video_content->streams()) {
        uint32_t ssrc = send_stream.FirstSsrc();
        if (ssrc != 0) {
            VideoReceiveStreamConfig config;
            config.el = el_;
            config.clock = clock_;
            video_receive_stream_ = std::make_unique<VideoReceiveStream>(config);
        }

        break;   // 只取第一条流
    }
}
```

配套新增 `StreamParams::FirstSsrc()`（`stream_params.h`）：`ssrcs` 非空时返回 `ssrcs[0]`。

代码看起来简单，但"取第一条流、只取一个 SSRC"这个写法背后有一套完整的协商格式推理，就是下面这场讨论。

## 二、讨论一：WebRTC 原生里 VideoTrack 的表现形式

### 发送侧

原生（native）客户端发视频的路径：

```
VideoSourceInterface（摄像头/桌面采集）
  → CreateVideoTrack(source)         // 拿到 webrtc::VideoTrackInterface
  → pc->AddTrack(track, {stream_id}) // 生成 RtpSender，track 绑定到 PC
  → 协商完成后，track 在 SDP 里"变成"一行行的 a=ssrc:
```

一条 `VideoTrack` 落在 SDP 里 = **一个 track_id + 一组 SSRC + msid 归属**：

| SDP 元素 | 含义 | 与 track 的关系 |
|---------|------|----------------|
| `a=ssrc:<n> cname:...` | 媒体 SSRC + CNAME | 主 SSRC |
| `a=ssrc:<m> cname:...` | RTX SSRC（重传专用） | 与主 SSRC 组成 FID 组 |
| `a=ssrc-group:FID <n> <m>` | 主 SSRC 与 RTX SSRC 绑定 | 一条 track 的完整传输身份 |
| `a=ssrc:<n> msid:<stream_id> <track_id>` | track 归属 | **track_id 就是 AddTrack 时 track 的 id** |
| `a=ssrc:<n> mslabel:<stream_id>` / `label:<track_id>` | 旧版 msid 写法 | 同上 |

关键点：**原生客户端发的每一条 VideoTrack，一定会贡献一组 `a=ssrc:` 行（至少一个媒体 SSRC，带 RTX 时再加一个 RTX SSRC）**。这是后面所有推理的出发点。

### 接收侧

对端收到后：`OnTrack(rtc::scoped_refptr<VideoTrackInterface> track)` 触发，接收端 PC 用收到的 SSRC 创建本地 `VideoTrack`，App 通过 `AddSink` 拿到视频帧渲染。我们 SFU 的 `VideoReceiveStream` 就是接收侧这一环（只不过我们拿到帧后不渲染，而是转发给 PullStream 的订阅者）。

## 三、讨论二：PlanB vs kUnifiedPlan（SDP 的组织方式差异）

两种格式解决的是同一个问题：**多路视频 track 怎么放进 SDP**。区别只在"怎么组织"，不在"SSRC 怎么表达"。

| 维度 | PlanB | UnifiedPlan（kUnifiedPlan） |
|------|-------|---------------------------|
| m=video 段 | **只有一条** `m=video`，多路 track 靠多组 `a=ssrc` + `a=ssrc-group` 挤在这一条 m-line 里 | **每条 track 一条** `m=video`（m-line 顺序 = AddTrack 顺序） |
| msid 位置 | 写在 `a=ssrc:<n> msid:...` 行上（每条 ssrc 行带归属） | 写在 m-line 上 `a=msid:<stream> <track>`（Chrome 为兼容也会在 ssrc 行再带一份 `a=ssrc:... msid:...`） |
| SSRC 表达 | `a=ssrc:` 行 + `a=ssrc-group:FID` | **完全一样的 `a=ssrc:` 行 + `a=ssrc-group:FID`** |
| 多路区分 | 靠 msid 里不同的 track_id | 靠不同的 m-line |
| 现状 | 已被废弃（deprecated），Chrome 只为兼容旧协商保留 | 现行默认 |

**两种格式里，SSRC 和 FID 分组的表达方式完全一致**，差别只在于"这组 ssrc 属于哪条 track / 哪条 m-line"这套归属信息的组织方式。而归属信息，恰恰是我们在接收端**不需要**的——见第五节。

## 四、讨论三：answer 镜像 offer 原则（RFC 3264）

这是整套推理的核心，也是"我们敢"的最大底气：

> **RFC 3264（Offer/Answer Model）：answer 里的 m-line 必须与 offer 一一对应——数量相同、媒体类型相同、顺序相同，且必须包含 offer 中每一个 m-line。answer 只能"回应" offer 里出现过的内容，不能凭空新增。**

也就是说：**SDP 协商时，格式是谁定的？offerer 定的。** answerer 只能在这个框架内填充自己的参数（端口、SSRC、codec、指纹……），不能改变 m-line 结构。

落到我们的系统（以 PUSH 为例，`CLAUDE.md` 的完整流程）：

```
signaling --PUSH--> SFU PushStream::CreateOffer()     ← 我们是 OFFERER
  → offer 原路返回给 VS2022 客户端
  → 客户端 createAnswer                              ← 客户端是 answerer
  → CMDNO_ANSWER --> SetRemoteSdp(解析 answer)        ← 我们解析的是 ANSWER
```

而我们 `CreateOffer` 生成的 offer 是**一条** `m=video`（`recv_video=true`，只有一个视频 content，`peer_connection.cpp:157-166`）。按镜像原则，客户端回来的 answer **必然只有一条 `m=video`**——不管这个客户端内部是 PlanB 模式还是 UnifiedPlan 模式。

于是第一个结论就出来了：

> **我们解析的不是"客户端任意发来的 offer"，而是"被我们自己的 offer 锁死了结构"的 answer。**
> 单 m=video 的 answer，PlanB 解析和 UnifiedPlan 解析拿到的是同一个东西。

## 五、结论：为什么我们敢用 PlanB 的方式解析 SDP

四条底气，按重要性排序：

### 1. answer 镜像 offer，m-line 结构被我们锁死

如第四节：我们是 offerer，offer 只有一条 `m=video`，answer 必然只有一条 `m=video`。解析器从头到尾只会碰到一个 video content。

### 2. 推拉流原子设计：一个 PC 一条视频流

代码注释就是设计原则："一个 peerconnection 只允许推一个或者拉一个视频"（`push_stream.cpp:38-40`：push 只 `recv_video`，pull 只 `send_video`）。所以即使出现多组 ssrc，也只会属于同一条视频流（主 SSRC + RTX SSRC 的 FID 组），`FirstSsrc()` 取到的一定是这条流的主 SSRC。

### 3. 我们的解析器本质上是"宽松的扁平化"，天然兼容 UnifiedPlan

看 `SetRemoteSdp` 的解析逻辑（`peer_connection.cpp:375-465`）：

```cpp
// 所有 m=video 段共用一个 video_content，不按 m-line 区分
if ("video" == media_type) {
    remote_desc_->AddContent(video_content);   // 同一个对象，不管几条 m-line
    ...
    ParseSsrcGroupInfo(video_ssrc_groups, field);  // 所有 a=ssrc-group 扁平收集
    ParseSsrcInfo(video_ssrc_info, field);         // 所有 a=ssrc 扁平收集
}
// 解析完统一按 track_id 分组 → 每条 track 一个 StreamParams
CreateTrackFromSsrcInfo(video_ssrc_info, video_tracks);
```

它**不关心 m-line 边界**，把所有 `a=ssrc:` 行全部收进一个列表再按 track_id 分组。这在 PlanB 语义下"正确"，在 UnifiedPlan 语义下同样"正确"——因为如前所述，两种格式里 `a=ssrc:` 行和 FID 组的写法完全一致，只是归属组织的粗细不同。

**即使将来某天我们要解析对方发来的任意 offer（比如我们改做 answerer），多 m=video 的 UnifiedPlan offer 被扁平化后，也能正确取出每条 track 的 ssrc 组**——只要每条 track 的 FID 组完整，分组逻辑就成立。

### 4. 我们只消费 SSRC 和 FID 组，不消费 msid 的多流语义

`VideoReceiveStream` 需要的全部信息：接收用的 SSRC（解 SRTP 后按 SSRC 认流）、RTX 关联（FID 组，将来做 NACK/RTX 恢复用）。CNAME、msid、track_id 这些"归属信息"我们一概不碰——而归属信息正是 PlanB/UnifiedPlan 差异最大的部分。**差异最大的部分我们不用，差异最小的部分（ssrc/ssrc-group）我们全用，这就是"敢"的技术基础。**

## 六、假设边界（什么情况下这套推理会翻车）

| 场景 | 影响 | 现状 |
|------|------|------|
| 客户端 offer 是多 track（摄像头 + 屏幕共享），且**我们是 answerer** | 我们的解析必须面对多 m=video / 多 track，`FirstSsrc + break` 只取第一条 | 当前架构我们是 offerer，不成立 |
| 一条流没有 RTX（无 FID 组，或 FID 只有主 SSRC） | `FirstSsrc` 仍取到主 SSRC，接收没问题；将来做 RTX 时按 FID 组查找要判空 | 兼容（`HasSsrc`/空组已有判断） |
| 客户端中途换 track（msid 变、SSRC 不变） | 我们不消费 msid，无感知，接收流不受影响 | 兼容 |
| 客户端协商出多路音频/视频 m-line 的 answer（理论上被镜像原则禁止） | 扁平化后第一条流仍可取，多余流被忽略 | 理论不发生，发生也不崩 |

## 七、一句话总结

> **SSRC 是传输层的身份，msid 是应用层的身份。我们作为 SFU 只认传输层身份；而 answer 镜像 offer 原则保证了协商结构永远是我们说了算。PlanB 和 UnifiedPlan 的差异全在应用层归属组织上，所以两种格式对我们来说是一回事——敢用 PlanB 解析，不是侥幸，是结构上的必然。**
