```cpp
    // ⑤ cumulative lost: 负值 offset + 24bit 封顶
    // ⑥ SetExtHighestSeqNum(received_seq_max_)
    //    SetJitter(jitter_q4_ >> 4)
    // ⑦ AndReset: 更新"上次报告基线"
}
```

`kStreamStatTimeoutMs = 8000`（8 秒），定义在 `receive_stat.cpp` 匿名 namespace。

## 二、fraction lost：差值法 + 255 不是 256

**差值法**：RFC 定义"自上次报告以来"的丢包比例，是**增量**。而接收端只维护累计量，所以取两次报告间的差：

```cpp
int64_t exp_since_last = received_seq_max_ - last_report_seq_max_;        // 本周期期望收
int32_t loss_since_last = cumulative_loss_ - last_report_cumulative_loss_; // 本周期丢包增量
if (exp_since_last > 0 && loss_since_last > 0) {
    stats.SetFractionLost(255 * loss_since_last / exp_since_last);
}
```

**255 而非 256（RFC 原文是 256）**：字段是 8bit 无符号（0~255），100% 丢包时 `256` 溢出成 `0`（灾难性误报 0% 丢包）。WebRTC 用 `255 * loss / exp`，100% 丢 = 255，永不溢出。

**填放条件 `exp > 0 && loss > 0`**：本周期没丢（`loss <= 0`）时字段默认 0 即可；`exp <= 0` 会除零。中间量用 int64（扩展 seq 是 32 位大数，差值防溢出）。

## 三、cumulative lost：负值 offset 线性平移（本课核心）

### 为什么内部 `cumulative_loss_` 会变负

4.7 账本模型：乱序/重传包到达时 `--cumulative_loss_` 后 **return 短路**（只撤销自己当初那笔账，不补差）。所以一个重传包就把账打到 -1；网络抖动来几个重传，账就负到 -5、-10：

```
收 1: -1 + 1 = 0
收 2: -1 + 1 = 0
收 3: -1 + 1 = 0
收 2(重传): -1  → return  账 = -1   ← 实收 > 期望, 账变负
```

而 RFC 规定 cumulative lost 字段**必须 ≥ 0**（24 位有符号，负值视为溢出）。

### 为什么不能直接 clamp 成 0

接收端（发包方）拿 RR 后要算"本周期丢了多少包"——取**相邻两个 RR 的 cumulative lost 做差分**。差分必须准确，否则丢包率/RTT 全错。看两种变换的性质：

| 处理方式 | 数学性质 | 负值区间 |
|---|---|---|
| `clamp(x)` | **非线性**（负数全压 0） | 信息全丢，差分失真 |
| `x + offset` | **线性平移**（整体加常数） | 信息保留，**差分不变** |

**具体例子**：内部从 -5 爬到 +5（重传逐渐被消化，开始真丢包），两个 RR 周期内：

```
clamp:     0 → 5     差分 = 5    ← 真实增量 10, 丢了 5 个的信息
offset:    0 → 10    差分 = 10   ← 真实增量 10, 分毫不差
```

clamp 是**非线性变换**，把负数区间信息压没了——内部明明多收了 5 个重传（净变化 10），报出的差分却只有 5。offset 是**线性平移**，差分永远等于内部真实差分，零信息损失。

### offset 的完整时间线

```
周期   内部    报出 = 内部 + offset      offset    发生了什么
─────────────────────────────────────────────────────────────
1       0      0 + 0 = 0     ≥0         0         正常, 不触发
2      -5     -5 + 0 = -5    <0         报 0 →    ← 触发: 报 0, offset 当场置 5
3      -4     -4 + 5 = 1     ≥0         5         已非负, 报 1 (内部还是负的!)
4      -2     -2 + 5 = 3     ≥0         5         报 3
5       1      1 + 5 = 6     ≥0         5         报 6
6       4      4 + 5 = 9     ≥0         5         报 9
```

**关键认知**：
1. "报一次 0"只在**触发那个周期**。周期 3 内部还是 -4（负值！），但报出 `-4+5=1` **已经不是 0**——offset 让"内部还是负"时也能报出非负值。
2. offset **不是每次补偿，是触发时永久定死**。置 5 之后只要内部 ≥ -5，报出恒 ≥ 0，后面全是 `内部 + 5`。
3. **何时再触发**：内部**跌破历史最低点**（offset 落后了）→ 报 0 + 刷新 offset 到新深度。所以 offset 永远定格在"历史最深负值"，破了纪录就重新平移。

### 一句话记忆

**clamp 是把负历史抹掉（信息丢），offset 是把整条曲线平移上去（差分准确，恒非负）——平移量 = 历史最深负值。**

## 四、0x7FFFFF 封顶

```cpp
if (packets_lost > 0x7FFFFF) {   // 24bit 有符号上限 2^23-1 = 8388607
    if (!cumulative_loss_is_capped_) {
        cumulative_loss_is_capped_ = true;   // 只告警一次, 防每周期刷屏
        RTC_LOG(LS_WARNING) << "cumulative packet loss reached max value for ssrc: " << ssrc_;
    }
    packets_lost = 0x7FFFFF;
}
```

超过上限会溢出成负数（写 3 字节时符号位翻转），封顶到最大值。课程里 800 万丢包实际到不了，是健壮性保护。

## 五、jitter：>>4 还原上报

```cpp
stats.SetJitter(jitter_q4_ >> 4);
```

jitter 是 **EWMA 状态，天然是当前值**，不需要差值。直接 `>>4` 还原（4.8 十一节讨论过的"上报还原，字段是整数不是 Q4 小数"在此落地）。

## 六、AndReset 重置的是"基线"不是"账本"

```cpp
last_report_seq_max_ = received_seq_max_;        // 只更新两个基线快照
last_report_cumulative_loss_ = cumulative_loss_; // cumulative_loss_ 原样保留
```

- **重置**：`last_report_seq_max_` / `last_report_cumulative_loss_`（供下周期 fraction lost 差值对比）
- **不重置**：`cumulative_loss_` 全程累计账本、`jitter_q4_` EWMA 状态

所以 `AndReset` 语义精确为：**把"上次报告的基线"推进到当前**，累计状态继续累积。
