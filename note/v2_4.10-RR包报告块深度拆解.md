# v2_4.10 RR 包报告块（Report Block）深度拆解

> 完成时间：2026-08-11
> 定位：**报告块专项**。`v2_4-RR包格式详解.md` 讲了整包总览（头 5 字段 + 两个 SSRC 的区别），本文把 **24 字节报告块逐字段拆到字节级**：RFC 3550 原文公式 + WebRTC 实际代码 + 带数字的计算示例。
> 配套代码：`rtcbase_v2/src/modules/rtp_rtcp/source/rtcp_packet/report_block.{h,cc}`、`receiver_report.{h,cc}`

## 〇、先记住整体形状

```
RR 包 = 8 字节公共头 + N 个 24 字节报告块（RC = N，最多 31）
公共头（本文不展开，见总览文档）：
  |V=2|P| RC | PT=RR=201 | length | SSRC of packet sender |
                                                              ← 头部就这 2 个字，后面全是报告块
报告块 × N（24 字节 = 6 个 32-bit 字，全部大端）：
  | SSRC_1 | fraction lost + cumulative lost | ext highest seq | jitter | LSR | DLSR |
```

**你已清楚的部分 = 公共头 + 头部 SSRC。本文剩下要啃的 = 报告块里那 24 字节。**

## 一、报告块位布局（带字节偏移，与 WebRTC `ReportBlock::Create` 对齐）

```
 ByteOffset   0         1         2         3
 0          ┌────────────────────────────────┐
            │         SSRC_1 (32b)           │  0~3
 4          ├────────────┬───────────────────┤
            │fraction    │ cumulative lost   │  4 / 5~7
            │lost (8b)   │ 24b (有符号!)      │
 8          ├────────────┴───────────────────┤
            │ extended highest seq num (32b) │  8~11
 12         ├────────────────────────────────┤
            │ interarrival jitter (32b)      │  12~15
 16         ├────────────────────────────────┤
            │ last SR / LSR (32b)            │  16~19
 20         ├────────────────────────────────┤
            │ delay since last SR / DLSR(32b)│  20~23
 24         └────────────────────────────────┘
```

WebRTC 代码对照（`report_block.cc` 的 `Create`，`ByteWriter::WriteBigEndian` = 大端写）：

| 字节 | 字段 | 写代码 | 校验/约束 |
|------|------|--------|----------|
| 0~3 | source_ssrc_ | `WriteBigEndian(&buf[0], source_ssrc())` | — |
| 4 | fraction_lost_ | `WriteBigEndian(&buf[4], fraction_lost())` | 单字节 |
| 5~7 | cumulative_lost_ | `WriteBigEndian<3>(&buf[5], ...)` | `RTC_DCHECK_LT(cumulative_lost, 1<<23)` |
| 8~11 | extended_high_seq_num_ | `WriteBigEndian(&buf[8], ...)` | — |
| 12~15 | jitter_ | `WriteBigEndian(&buf[12], ...)` | — |
| 16~19 | last_sr_ | `WriteBigEndian(&buf[16], ...)` | — |
| 20~23 | delay_since_last_sr_ | `WriteBigEndian(&buf[20], ...)` | — |

## 二、逐字段拆解（重点）

### 1. SSRC_1（32b）— 被报告的发送端 SSRC
简单：这个块在汇报谁。多块时每块一个不同的媒体 SSRC。

### 2. fraction lost（8b）— 近期丢包率，定点小数

RFC 3550 原文：自上次发 SR/RR 以来丢失的比例，**定点数，小数点在最左端**——即"丢包分数 × 256 取整数部分"。

- 范围 0~255，映射 0%~100%（256 = 满格 100%）
- **实际算法（WebRTC 用差值法，不用维护比例状态）**：

```
fraction lost = (期望收 - 实收) * 256 / 期望收     ← 区间内（本次报告周期内）
```

**数字例子**：本周期期望收 200 包（序列号从 50000 到 50199），实收 150 包
```
fraction lost = (200 - 150) * 256 / 200 = 64   → 64/256 = 25%
```
不丢包 = 0，全丢 = 255。

> 为什么用"差值"而不是"累计"：RFC 的定义是"自上次报告以来"，需要的是**增量**。而接收端只维护累计量，所以做法是 `本次累计 - 上次累计`（4.11 里 `MaybeAppendReportBlockAndReset` 的 "AndReset" 就是干这个——取完差值把累计账本 reset 成周期起点）。

### 3. cumulative lost（24b，**有符号**！）— 累计丢包数

RFC 3550 原文：自**开始接收以来**的总丢包数。注意它是 **signed 24-bit**。

- 为什么有符号：乱序/重传会导致"实收 > 期望"（收到重复包），丢包数变**负**。RFC 说负值视为重复溢出，应截断为 0；**WebRTC 保留负值**（`cumulative_lost_` 是 `int32_t`，`SetCumulativeLost` 只校验 `< 2^23`，写 3 字节时符号位自然带上）
- 上限 ±2^23-1（约 838 万包），超出即溢出

```
cumulative lost = 最大扩展序列号 - 初始扩展序列号 + 1 - 实收数      ← 全程累计，不是周期增量！
```

**数字例子**：开始收时 ext seq = 50000，现在 ext seq max = 50199，实收累计 150
```
期望收 = 50199 - 50000 + 1 = 200
cumulative lost = 200 - 150 = 50
```

### 4. extended highest seq（32b）— 扩展最高序列号

RFC 3550：低 16 位 = 收到的最高序列号；**高 16 位 = 序列号回绕次数**。

- 16 位序列号 0~65535 会回绕，扩展后变成单调递增的 32 位大数，丢包/期望计算全靠它
- 与 4.6 学的 `seq_unwrapper_` 对应：unwrap 出的就是扩展序列号

```
extended highest seq = (回绕次数 << 16) | 当前最高序列号
```

**数字例子**：回绕过 1 次（65536 以上），当前最高 seq = 50199
```
= (1 << 16) | 50199 = 65536 + 50199 = 115735
```

### 5. interarrival jitter（32b）— 抖动，单位是 RTP timestamp tick

RFC 3550 公式（一阶低通滤波，α=1/16）：

```
J(i) = J(i-1) + ( |D(i-1,i)| - J(i-1) ) / 16
D(i,j) = (Rj - Ri) - (Sj - Si)         ← 到达间隔差 = (到达时间差) - (时间戳差)
```

- 单位是 **RTP timestamp tick**（视频 90kHz，1 tick ≈ 11µs），**不是毫秒**（4.8 的坑）
- 本工程 4.8 用 **Q4 定点** `jitter_q4_` 累积（防小数丢失），**上报时 >> 4 还原**：
  - 例子：`jitter_q4_ = 1280` → 上报 `1280 >> 4 = 80` tick → 80/90000 ≈ 0.89ms

### 6. LSR（32b）— 最近 SR 的 NTP 压缩时间

RFC 3550：最近收到的 SR 包里的 NTP 时间戳的**中间 32 位**（64 位完整 NTP 太长，取中间 32 位足够精度）。

```
NTP 64 位: [秒(32b)] [1/2^32 秒的小数(32b)]
                └───── 中间 32 位 = 秒的高 16 位 + 小数的低 16 位 ─────┘
LSR = 秒的高 16 位 << 16 | 小数的低 16 位
```

- 没收到过 SR → LSR = 0
- 谁填：`RTCPReceiver::HandleSr` 保存（本工程 3.11 空实现，4.12/4.14 填）

### 7. DLSR（32b）— 收到 SR 后磨蹭了多久才发本 RR

RFC 3550：从收到最近那个 SR 到发出本报告块之间的延迟，**单位 1/65536 秒**（又是定点数）。

```
DLSR = (发出 RR 的时刻 - 收到 SR 的时刻) * 65536
```

- 没收到过 SR → DLSR = 0
- 例子：收到 SR 后 100ms 发 RR → `0.1 * 65536 = 6553.6 ≈ 6554`

## 三、最容易混的 3 个点（面试/联调自查）

| 易混点 | 真相 |
|--------|------|
| fraction lost vs cumulative lost 的时间窗 | fraction = **上次报告以来**（增量，需要 reset 账本）；cumulative = **开始以来**（全程累计） |
| LSR 取"中间 32 位" | 不是取高 32 位也不是低 32 位——`(ntp.sec << 16) | (ntp.frac >> 16)`，高位秒 + 低位小数各一半 |
| DLSR 单位 | 1/65536 秒，不是毫秒。算 RTT 时三个量（A/LSR/DLSR）必须统一到 1/65536 秒再减 |

## 四、RTT 闭环（报告块终极用途）

```
RTT = A - LSR - DLSR
  A    = 发送端收到 RR 时自己的 NTP 压缩时间（"现在"）
  LSR  = 发送端上次发 SR 的时刻（RR 带回来的，报告块第 6 字段）
  DLSR = 接收端收到 SR 后磨蹭的时间（报告块第 7 字段）
```

```
发送端 ──SR(NTP=t0)──▶ 接收端 ──(收到SR后 DLSR 时间)── RR(LSR=t0, DLSR) ──▶ 发送端
发送端现在 = t1 ──┐
                  ├─ t1 - t0 = 单程×2 + DLSR  →  RTT = (t1 - t0) - DLSR = A - LSR - DLSR
LSR = t0 ─────────┘
```

## 五、完整数字演练（一包 RR 从统计到字节）

场景：媒体 SSRC=1000，视频 90kHz，回绕 1 次，90ms 前收到过 SR。

```
fraction lost      = 64        (25%)
cumulative lost    = 50        (24b 有符号: 0x000032)
ext highest seq    = 115735    (0x0001C417, 高16位=回绕1次, 低16位=0xC417)
jitter             = 80        (jitter_q4_=1280 >> 4)
LSR                = 0xE2E31234 (例子)
DLSR               = 6554      (0.1s × 65536)

序列化后 (24 字节, 大端):
00 00 03 E8 | 40 00 00 32 | 00 01 C4 17 | 00 00 00 50 | E2 E3 12 34 | 00 00 19 9A
└─ SSRC_1 ─┘ └ fl=64 ─────┘ └ ext seq ───┘ └ jitter ───┘ └ LSR ─────┘ └ DLSR ───┘
```

放进 RR 包：`CreateHeader(report_blocks_.size(), kPacketType, ...)` —— **RC 字段 = 块个数**，`receiver_report.cc:93` 校验 `size >= kMaxNumberOfReportBlocks(31)` 拒绝再加块。整包 `length = 1 + RC*6`（1 块时 = 7，32 字节）。
