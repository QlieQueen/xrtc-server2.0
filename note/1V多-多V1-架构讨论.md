# 1V1 → 1V多 → 多V1 架构讨论（含 SFU vs MCU）

> 本文是围绕 xrtc-server2.0（WebRTC 媒体服务 / SFU）的架构概念讨论沉淀。
> 对应参考课程：`xrtc2.0-9.9`（1V多 主干在 7.x，8.x 补 PLI，9.x 补下行 SR）。

---

## 一、原子单元：1 对 PC（一切形态的本质）

整个系统无论叫"几 V 几"，最小媒体单元都是：

```
1 对 PC = 1 个 push PC ↔ 1 个 pull PC
        = 1 个 RTP/SRTP session 对（内部 SSRC 唯一、DTLS/ICE 独立）
```

所有形态都是这个单元的组装：

| 形态 | 从 PC 视角 | 本质 |
|------|-----------|------|
| **1V1** | 1 对 PC | 基础单元 |
| **1V多** | 1 个 push PC + N 个 pull PC | push 侧的扇出聚合（`multi_pull_streams_`） |
| **多V1** | N 对 (push PC + pull PC) 并行 | N 条 1V1 的并行集合，无新语义 |

**推论**：从 PC（session）视角看，**没有真正的"多"**——永远是一对一。
- `multi_pull_streams_`（stream → uid → PullStream）只是"扇出"的聚合容器，不是新的媒体实体
- RTP 转发的本质 = 把一个 push PC 收到的包，复制投递到同 stream 名下 N 个 pull PC 各自的 SRTP send session
- 数据结构和信令只需围绕"PC 对"这一个单元设计；"多"只是按 stream_name 的复制聚合
- 这也是当前架构能同时覆盖 1V1 / 1V多 / 多V1 而不改媒体层的原因

## 二、1V1 如何演变成 1V多

### 演进路径（对应课程）

```
1V1（当前 2.0 基线 = xrtcserver_v2）
  └─ 7.3  引入 transparent / live 双传输模式
  └─ 7.4  新增 multi_pull_streams_：unordered_map<stream, unordered_map<uid, PullStream*>>
  └─ 7.5  RemovePullStreamM 按 uid 清理多拉流（生命周期）
  └─ 7.6  CreatePull / SetAnswer / StopPull 按 mode 分流
  └─ 7.7  live 模式 RTP 上报链：OnRtpPacket → PC::SignalRtpPacket → PushStream → manager
  └─ 7.8  OnRtpPacket 把 push 的 RTP 广播给该 stream 名下所有 pull（一推多拉）
  └─ 8.2~8.3  PLI 周期关键帧请求（新拉流端快速出画）
  └─ 9.x  每路 pull 变成带发送统计 + SR 下行上报的完整 RTP 发送端
```

### 关键数据结构

```cpp
std::unordered_map<std::string, PushStream*> push_streams_;   // 单值：1 stream = 1 push（写死）
std::unordered_map<std::string, PullStream*> pull_streams_;   // 1V1 用（单值）
PullStreamMap multi_pull_streams_;                            // 1V多：stream → uid → PullStream
```

- `CreatePushStream`：同 stream_name 重复推会先 erase + delete 旧的，再重建 → **一个 stream 只能一个 push**（这是"仅 1V多"的架构原因）
- 转发为 **SSRC 透传**（`PullStream::SendPacket` 只 Parse 就 `pc->SendPacket`，不重写 SSRC）→ 同一流的所有拉流端看到相同 SSRC，本来就应该一致

## 三、多V1 的两种形态（单 PC vs 多 PC）

"多V1" = 1 个实体拉流端看 N 路推流。**是否要处理 SSRC 冲突，取决于「用户 ↔ PC」是 1:1 还是 1:N**。

### 形态 A：多 PC（1 用户 = N 个 PeerConnection）★ 当前架构

```
推流端A --SSRC=X--> SFU --SSRC=X(透传)--> 拉流端X 的 PC#1
推流端B --SSRC=X--> SFU --SSRC=X(透传)--> 拉流端X 的 PC#2   ← 跨路撞 SSRC 无害
```

- 每路是**独立 RTP/SRTP session**（独立密钥、独立接收状态机）
- SSRC 只在**单个 session 内**做媒体路由；跨路即使撞 SSRC，按 PC 实例隔离，**不混淆**
- **不需要处理 SSRC 冲突**；额外成本 = N-1 套会话状态 + N 路 ICE/DTLS 控制面（低频，中小规模可忽略）
- 客户端（VS2022 rtcclient_win）需支持多 PC 同时运行

### 形态 B：单 PC（1 用户 = 1 个 PeerConnection，N 路多 m-line）

```
推流端A --SSRC=X--> SFU ─┐
                        ├─> 拉流端X 的 1 个 PC（1 个 session）
推流端B --SSRC=X--> SFU ─┘   视频 m-line 冲突，无法区分谁是谁 ✗
```

- 所有路挤在**一个 RTP session**，SSRC 必须全局唯一
- **必须由 SFU 对下行重写 SSRC**（每路分配唯一值，且同步改 RTX 映射、RTCP SR/RR、PLI 里的 ssrc）
- 这是 mediasoup 那类 SFU 的典型做法，实现很重

### 本质统一

**SSRC 冲突的边界 = SRTP session 的边界**：
- 1 个 SRTP session = 1 个 DTLS 导出密钥 + 1 个对端 + 1 个 role，内部所有流共享加密上下文，SSRC 必须唯一
- 「1 = 一个 PC」→ 1 个 session → 多路必然冲突
- 「1 = 一个用户，底层 N 个 PC」→ N 个 session → 跨 session 撞 SSRC 无感

所以**从 PC 视角，多V1 本质上仍然是 1V1**——N 条独立链路的并行集合，没有超出 1V1 的新媒体语义。

## 四、单 PC 多流时，客户端起了多个解码器实例

### 解码器怎么"知道"有几路流？

不是"发现"的——**流数量在 SDP 协商阶段就声明死了**。N 路视频 = SDP 里有 **N 个 `m=video` 行**：

```
m=video 9 UDP/TLS/RTP/SAVPF 96 97
a=mid:0
a=ssrc:1000 cname:xxx            ← 流1 的 video SSRC
a=ssrc-group:FID 1000 1001       ← 流1 的 RTX
m=video 9 UDP/TLS/RTP/SAVPF 96 97
a=mid:1
a=ssrc:2000 cname:xxx            ← 流2 的 video SSRC
a=ssrc-group:FID 2000 2001       ← 流2 的 RTX
```

一个 `m=video` = 一路视频，带 `a=msid:<stream> <track>` 关联到 MediaStream + VideoTrack。

### 收端路由

```
收到 RTP 包 → 解析 SSRC（=2000）→ 查表：属于 mid:1
  → 投递到 mid:1 的 VideoReceiveStream → 该流的解码器实例 → 输出 VideoTrack
```

### 多个解码器实例（一路一个，必须）

- **是的，N 路 = N 个解码器实例**（一路 = 一个 `VideoReceiveStream` = 它管理一个解码器）
- **为什么必须**：解码器是**有状态**的——
  - 参考帧列表（H264 P/B 帧依赖前几帧）
  - SPS/PPS 参数集（每路独立）
  - 帧序号连续性 + NACK 重传逻辑
  - 独立时间线/时钟
  - 两路混进一个解码器，参考帧/时间线打架 → 直接崩
- 类比：解码器 = 一个"翻译官"，一次只能翻译一个人的话；N 路 = N 个翻译官
- 算力是**线性合理成本**：N 路画面本来就要 N 份解码算力。硬件解码 = 同一芯片开 N 个 codec context（会话）；软件解码 = N 个对象实例（OpenH264 句柄）
- 应用层：每路一个 VideoTrack 绑一个视频 sink，**布局是应用的事**（网格/画中画）

## 五、为什么主流用 SFU 而非 MCU

### MCU vs SFU

| | MCU（服务器合流） | SFU（当前工程） |
|---|---|---|
| 服务器 | **解码 N 路 → 拼接 → 编码 1 路**，算力/成本爆炸 | 只转发 RTP 包，几乎不算力 |
| 客户端 | 只解 1 路，成本最低 | 解 N 路，成本随路数线性涨 |
| 延迟 | 高（等所有路对齐 + 重编码） | 低（不重编，包级转发） |
| 画质 | 降（重编码损失 + 画面缩小） | 原汁原味 |
| 扩展 | 服务器是瓶颈（编码算力） | 服务器易水平扩展 |

### 业界事实

- WebRTC 会议主流全是 SFU：**Zoom（自研 SFU）、Google Meet（SFU）**
- 早年 MCU 在硬件视频会议时代是主流（算力集中在专用硬件），WebRTC 时代被 SFU 取代
- 原因：成本从客户端挪到服务器且更大（N 路解码+合成+编码）、合流延迟致命、重编码伤画质

### MCU 真正该用的地方

1. **录制**：N 路合流存成一路视频文件（回放不需要 N 路）
2. **传统直播/RTMP 推送**：下游播放器只认一路
3. **低端设备降级**：老人机/低端盒子解不动多路，服务器单独合成一路低码流
4. **大屏监控**：观众只关心整体画面

### 业界标准解法：SFU + 按需订阅（Simulcast / SVC）

客户端成本**不靠合流**解决，而靠推流端发多清晰度层（720p/360p/180p），SFU 按客户端能力/带宽决定发哪几层。低端设备少订阅几路或低清层，服务器零算力、客户端成本可控。

### 对当前工程的建议

```
① SFU + 按需订阅（Simulcast 层级）  ← 业界标准，服务器零算力
② SFU + 可选录制合流（做一路文件）   ← 需求明确再加
③ 真 MCU（实时合流给观众）          ← 算力贵，一般不做
```

当前课程（9.9）连 Simulcast 都没有（单清晰度透传）。真往低端设备走，补 Simulcast 比补 MCU 划算得多。

---

## 六、一句话总结

> **架构的最小单元是"1 对 PC"（1V1），1V多 是多拉流端的扇出、多V1 是多条 1V1 并行——从 PC 视角没有"多"。多 PC 形态天然规避 SSRC 冲突；单 PC 多 m-line 才需要 SFU 重写 SSRC，且客户端会为每路起一个解码器实例。客户端解码成本的最优解是 SFU + Simulcast 按需订阅，而不是服务器合流的 MCU。**
