# v2_10.7 下行 RTX 重传风暴问题记录

> 日期：2026-08-24（云上测试发现，待明天继续排查）
> 状态：**未解决**，方向指向 12.x 下行 NACK 恢复

## 现象

- 环境：云服务器（3M 带宽）
- 场景：1 推流 + **2 拉流**（IPC 摄像头风格测试）
- 结果：**下行流量爆到 10M**（远超 3M 带宽上限），其中 **~30% 是 RTX 重传包**

## 根因分析（当前判断）

10.x 的重传实现是**裸重传**：`RtcStreamManager::OnNackReceived` 无条件遍历 nack_list 全部重传，
**无去重、无重传次数上限、无 RTT 退避**。这形成正反馈自激振荡：

```
下行拥塞/丢包 → 拉流端 NACK → 服务端立即重传
  → 重传挤占带宽 → 更拥塞 → 丢更多包 → 更多 NACK → 更多重传
                         ↑ 循环放大
```

次要嫌疑（待验证）：拉流端是否真正识别 RTX 包——
- 服务端 offer 是否协商了 rtx codec（a=rtpmap:xx rtx/90000 + a=fmtp apt= 映射）？
- 拉流端不认 RTX 则永远恢复不了画面 → 对同一批 seq 反复 NACK → 服务端反复重传同一批包

## 待验证点（明天）

1. 服务端日志：同一 seq 是否被**反复 NACK**（重传循环的直接证据）
2. 拉流端画面：重传期间是否恢复（一直花屏 = RTX 没被客户端吃进去）
3. 本地局域网复测，与云上对比（排除 3M 带宽本身拥塞的因素）

## 解决方向

**12.x 下行 NACK 恢复**（v12.1 ~ v12.4）：
`rtcp_receiver 大改 + nack_requester/video_receive_stream 联动`——
重传去重、每包重传次数限制、超时放弃、RTT 退避，从根上防风暴。

## 附加价值

真实环境踩坑素材：面试可讲"裸重传在拥塞下会风暴，需 nack_requester 节流"。
