## 一、RTX 是什么：为什么不能走原路重传

NACK 请求推流端重发丢失的包。**重传包如果走原通道回来，会和"乱序包"混淆**：同样一个 seq=100，你分不清它是"本来就该来的乱序包"还是"NACK 求来的重传包"——接收统计、组帧都会算错。

所以开一条**专用重传通道（RTX）**，用明显标记一眼认出"这是重传的"：

| | 主媒体流 | RTX 重传通道 |
|---|---|---|
| Payload Type | 98（H264） | **99（rtx）** |
| SSRC | 主媒体 SSRC | **独立 RTX SSRC** |
| seq | 媒体序号（独立递增） | **独立 rtx seq（独立递增）** |

**RTX 通道的 seq 与主通道完全无关，各数各的。** 只要看到 PT=99，就知道是重传包，绝不可能和主媒体流混淆。

SDP 里的声明（`session_description.cpp` 生成）：

```
a=rtpmap:98 H264/90000
a=rtpmap:99 rtx/90000        ← 重传通道
a=fmtp:99 apt=98             ← apt = 关联到 98（原媒体 PT）
```

`apt`（Associated Payload Type）说明"rtx=99 通道是用来重传 98 的包的"。

## 二、RTX 包格式

```
┌── RTP 头(PT=99, SSRC=rtx_ssrc, seq=rtx_seq) ──┬── OSN(2字节) ──┬── 原始媒体数据 ──┐
```

RTX 包比普通包**多了 2 字节 OSN**，紧贴 payload 最前面：

```
Byte 0      1     2   3     ...
      ┌──────┬──────┬────────────────────┐
      │OSN高8位│OSN低8位│  原始payload(媒体数据)  │
      └──────┴──────┴────────────────────┘
```

**OSN（Original Sequence Number）= 被重传的那个包的原始媒体序号，大端序（高字节在前）。**

## 三、RTP 头"哪同哪不同"——决定恢复改什么

RTX 包 RTP 头**格式**与源包完全一样（标准 12 字节），但**字段值有同有不同**：

| RTP 头字段 | RTX 包 | 源媒体包 | 恢复时 |
|---|---|---|---|
| **PT** | 99（rtx） | 98（H264） | **改回 98** |
| **SSRC** | rtx_ssrc（独立） | 主媒体 SSRC | **改回主 SSRC** |
| **seq** | rtx_seq（独立递增） | 媒体 seq | **改成 OSN** |
| **timestamp** | **复制源包** | 源包 timestamp | **不动** |
| **M 位** | **复制源包** | 源包 M 位 | **不动** |

要点：
- **PT/SSRC/seq** 是 RTX 通道的身份标记 → 恢复时**改回**原始值，恢复包才能和主媒体流"认亲"（PT 对 codec、SSRC 对归属、seq 对排序）。
- **timestamp/M 位** 复制源包 → 恢复时**原封不动**，保证恢复包放进帧里不乱（同帧 timestamp 一致、M 位标记帧尾）。

**所以恢复只动 seq/PT/SSRC 三样，timestamp 和 M 位原样保留。**

> RFC 4588 附加规定：RTX 包不允许 padding，一般不携带 RTP header extension。

## 四、RtxReceiveStream 类设计

```cpp
class RtxReceiveStream {
public:
    RtxReceiveStream(RtpVideoStreamReceiver* media_sink,
            uint32_t media_ssrc,
            const std::map<int, int> rtx_associated_payload_types,  // <rtx_PT, 媒体_PT>
            ReceiveStat* rtp_receive_stat);
    ~RtxReceiveStream();

    void OnRtpPacket(const webrtc::RtpPacketReceived& rtx_packet);

private:
    RtpVideoStreamReceiver* media_sink_;          // 恢复后的包喂回媒体接收端
    uint32_t media_ssrc_;                          // 原媒体 SSRC（恢复时 SetSsrc）
    std::map<int, int> rtx_associated_payload_types_;  // 识别 RTX + 拿恢复后 PT
    ReceiveStat* rtp_receive_stat_;                // 恢复包统计（标记 recovered）
};
```

| 成员 | 职责 |
|------|------|
| `rtx_associated_payload_types_` | `map<rtx_PT, 媒体_PT>`：**查得到 = 是 RTX 包（识别）**，同时给出恢复后的媒体 PT。可支持多路 RTX 通道对应多路媒体 codec |
| `media_ssrc_` | 恢复时 `SetSsrc` 回原媒体 SSRC |
| `media_sink_` | 恢复完的包喂回 `RtpVideoStreamReceiver`，走正常组帧链路 |
| `rtp_receive_stat_` | **恢复包在这里统计**（见六、统计分工） |

## 五、OnRtpPacket 恢复五步（设计蓝图，6.5/6.6 实现）

> 本课（6.4）`OnRtpPacket` 保持空实现（框架）。以下五步是后续实现的设计蓝图，先看全貌再落地。

```
OnRtpPacket(rtx_packet)
  │
  │ ① 查表：rtx_associated_payload_types_[rtx_packet.PayloadType()]
  │    ├─ 查不到 → 不是认识的 RTX 通道，丢弃 return
  │    └─ 查到 → media_payload_type（恢复后的媒体 PT）
  │
  │ ② 读 OSN：payload 前 2 字节，大端 (payload[0] << 8) | payload[1]
  │    校验 payload_size() >= kRtxHeaderSize(2)，否则丢弃
  │
  │ ③ 构造恢复包 recovered_packet（拷贝 RTX 包，保留 timestamp/M）
  │    ├─ SetSequenceNumber(OSN)              ← seq 换回原始媒体序号
  │    ├─ SetPayloadType(media_payload_type)  ← PT 换回原媒体 PT
  │    ├─ SetSsrc(media_ssrc_)                ← SSRC 换回原媒体 SSRC
  │    ├─ 去 OSN：SetPayloadSize(size-2) + memmove 前移 2 字节
  │    └─ set_recovered(true)                 ← 标记：这是恢复出来的包
  │
  │ ④ rtp_receive_stat_->OnRtpPacket(恢复包)  ← 统计（知道它是重传补上的）
  │
  │ ⑤ media_sink_->OnRtpPacket(恢复包)        ← 喂回正常组帧链路
  │
  ▼
```

代码骨架：

```cpp
void RtxReceiveStream::OnRtpPacket(const webrtc::RtpPacketReceived& rtx_packet) {
    // ① 识别 + 得恢复后 PT
    auto it = rtx_associated_payload_types_.find(rtx_packet.PayloadType());
    if (it == rtx_associated_payload_types_.end()) {
        return;  // 不是认识的 RTX 通道
    }
    int media_payload_type = it->second;

    // ② 读 OSN（大端）
    if (rtx_packet.payload_size() < kRtxHeaderSize) {
        return;
    }
    uint16_t original_seq_num =
            (rtx_packet.payload()[0] << 8) | rtx_packet.payload()[1];

    // ③ 构造恢复包
    webrtc::RtpPacketReceived recovered_packet(rtx_packet);  // 拷贝 RTP 头(timestamp/M 保留)
    recovered_packet.SetSequenceNumber(original_seq_num);
    recovered_packet.SetPayloadType(media_payload_type);
    recovered_packet.SetSsrc(media_ssrc_);
    size_t media_payload_size = rtx_packet.payload_size() - kRtxHeaderSize;  // 去 OSN
    uint8_t* media_payload = recovered_packet.SetPayloadSize(media_payload_size);
    memmove(media_payload, rtx_packet.payload().data() + kRtxHeaderSize, media_payload_size);
    recovered_packet.set_recovered(true);

    // ④ 统计恢复包
    if (rtp_receive_stat_) {
        rtp_receive_stat_->OnRtpPacket(recovered_packet);
    }

    // ⑤ 喂回媒体接收端
    media_sink_->OnRtpPacket(recovered_packet);
}
```

需要补充的常量：`constexpr size_t kRtxHeaderSize = 2;`（rtx_receive_stream.cpp 匿名命名空间）。

## 六、与现有链路的关系

### 统计分工（rtp_receive_stat_ 为什么在这）

`RtpVideoStreamReceiver::OnRtpPacket` 里有：

```cpp
if (!packet.recovered()) {
    rtp_receive_stat_->OnRtpPacket(packet);  // 只统计真实到达的包
}
```

**恢复包走那条路会被跳过统计**。所以设计是：恢复包由 `RtxReceiveStream` 自己喂统计（标记 recovered，丢包率/jitter 知道它是重传补上的），再调 `media_sink_->OnRtpPacket` 只走组帧、不重复统计。职责分工：

```
普通包:  收包 → RtpVideoStreamReceiver::OnRtpPacket → 统计(真实到达) + 组帧
RTX 包:  收包 → RtxReceiveStream::OnRtpPacket → 恢复 + 统计(recovered) → 组帧
```

### recovered 标记贯穿链路

- `recovered() = true`：RTX/FEC 恢复出来的包
- 统计排除（不歪曲丢包率/jitter）——5.1 已写好
- NackRequester 接入后：恢复包应跳过缺失记账/不再点名（6.6 接入时处理）
- PacketBuffer 组帧：恢复包按原始媒体 seq 排序，正好补进缺口

## 七、一句话记忆

> **RTX = 重传专用通道（独立 PT/SSRC/seq）**。包格式：RTP 头 + **OSN（2 字节大端，被重传包的原始媒体序号）** + 媒体数据。**恢复 = 只改三样（seq←OSN、PT←apt、SSRC←媒体 SSRC），timestamp/M 原样**，再去掉 OSN、标 `recovered`，包就变回普通媒体包走正常组帧。识别靠 `map<rtx_PT, 媒体_PT>` 查表——查得到是 RTX，查到的 value 就是恢复后的 PT。
