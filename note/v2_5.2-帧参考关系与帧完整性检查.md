## 一、帧的参考关系

| 帧类型 | 参考关系 | 实时流用不用 |
|--------|---------|:---:|
| **I 帧（IDR）** | 帧内编码，**不依赖任何帧**，可独立解码 | ✅ 关键帧 |
| **P 帧** | **前向参考**：只依赖前面的参考帧 | ✅ 普通帧 |
| **B 帧** | 双向参考（依赖前后帧） | ❌ 不用（引入延迟，WebRTC 无 B 帧） |

无 B 帧时：**解码顺序 = 接收顺序**，参考链是一条单向链：

```
I → P1 → P2 → P3 → P4
```

两个推论：
- **断链连锁**：链上任一帧坏 → 之后所有 P 帧参考断裂，直到下一个 I 帧才恢复
- **关键帧是唯一"重新锚定"机会**——接收端丢帧后请求新关键帧（PLI，8.x）就是这个原因

## 二、帧内完整性检测算法：一帧的包收齐没

### 2.1 数据结构：环形 vector + continuous 字段

```
buffer_: std::vector<std::unique_ptr<Packet>>（大小是 2 的幂，如 512→2048 动态扩容）
槽位   = packet->seq_num % buffer_.size()     ← 环形缓冲，seq 直接映射槽位
```

每个 Packet 有 **`continuous` 字段**：标记**截止到该包为止，前面的 seq 是否全部连续**。它是**可传递**的：

```
prev.continuous && prev.seq == seq-1 && 同 timestamp → 本包也置 continuous
```

### 2.2 两个触发条件 + 三道闸门（PotentialNewFrame）

**触发检测**的两个条件（任一成立就认为"可能成新帧"）：

1. **收到帧的第一个包**（`is_first_packet_in_frame`）
2. **收到某个包时，它前面的包都连续了**（`prev_entry->continuous`）

但条件 2 前面还有三道闸门（不是只看 continuous）：

```cpp
// modules/video_coding/packet_buffer.cc:195
bool PacketBuffer::PotentialNewFrame(uint16_t seq_num) const {
  size_t index = seq_num % buffer_.size();
  int prev_index = index > 0 ? index - 1 : buffer_.size() - 1;
  const auto& entry = buffer_[index];
  const auto& prev_entry = buffer_[prev_index];

  if (entry == nullptr)                  return false;
  if (entry->seq_num != seq_num)         return false;   // 槽位被环回旧包占着

  if (entry->is_first_packet_in_frame()) return true;    // 触发 ① 收到帧首包

  if (prev_entry == nullptr)             return false;
  if (prev_entry->seq_num != static_cast<uint16_t>(entry->seq_num - 1))
                                         return false;   // 闸1：seq 必须紧邻（防环形槽位冲突）
  if (prev_entry->timestamp != entry->timestamp)
                                         return false;   // 闸2：必须同帧（timestamp = 帧边界）
  if (prev_entry->continuous)            return true;    // 触发 ② 前面全连续
  return false;
}
```

- **闸 1（seq 紧邻）不是废话**：环形缓冲里 seq 相差恰好一个 buffer 大小的包会撞同一个槽位，必须确认 prev 真的是 seq-1
- **闸 2（同 timestamp）是帧边界判断**：prev 连续但 timestamp 不同 = 上一帧的包，不能把跨帧的包当连续

### 2.3 触发后的组帧动作（FindFrames）

```cpp
// 触发后（FindFrames 主循环）：
for (i < buffer_.size() && PotentialNewFrame(seq_num)) {
  buffer_[index]->continuous = true;          // ① 置 continuous
  if (buffer_[index]->is_last_packet_in_frame()) {  // ② 末包到了才尝试组帧
    // 从末包 seq 往回搜 is_first_packet_in_frame
    // 中间的包全 continuous → 一整帧吐给上层（RtpFrameObject，5.4）
    // H264 关键帧判定：SPS/PPS/IDR NAL type（sps_pps_idr_is_h264_keyframe_ 开关）
  }
  ++seq_num;                                  // ③ 继续查下一个 → 一口气吐出连续多帧
}
```

### 2.4 关键认知

- **PacketBuffer 是"等齐再吐"**：缺首包等首包，缺中间包等中间包（或 NACK），缺末包等末包
- **帧内完整性 = 四条件**：首包标记（帧首）+ seq 连续（无缺口）+ 同 timestamp（帧内）+ 末包标记（帧尾，M 位补的）
- **帧内检测不懂 codec**：只用 RTP 头通用字段（timestamp/seq/M 位/首包标记），与 H264/H265 无关

## 三、帧间完整性检查算法：参考链断没断

**输入**：PacketBuffer 连续吐出的完整帧序列。

```
① 看帧类型：
   关键帧（IDR）→ 不依赖前面 → 帧内完整即可解码 ✓
   P 帧 → 继续 ②
② 查参考帧：本帧的前一帧是否完整/可解码？
   参考帧完整 → 本帧可解 ✓
   参考帧缺失/丢弃 → 本帧即使包全齐也是废帧 ✗ → 丢弃
③ 断链后的策略：丢弃后续所有 P 帧，直到下一个关键帧
   （或主动发 PLI 向对端要新关键帧，快速重建参考链）
```

**分层对照**：

| 检查 | 在哪一层做 | 课程 |
|------|-----------|------|
| 帧内完整性 | **PacketBuffer**（seq/timestamp/M 位，不懂 codec） | 5.3~5.5 |
| 帧间完整性 | **PacketBuffer 之上**（帧序列连续性、关键帧识别） | 5.5 OnFrame 层 + 8.x |
| 帧内检测失败的自救 | NACK（要单个 seq 的包，赶得上解码时刻就等） | 6.x |
| 帧间断链的自救 | PLI（要新关键帧，重建参考链） | 8.x |

### 3.2 三层职责对照：一个丢包例子走全流程

场景：P帧1 = 100 101 102 104（**103 丢**），P帧2 = 105 106 107（**完整**）。

**PacketBuffer 层（5.3~5.5）——P帧2 正常组帧吐出**

```
105 到达 → PotentialNewFrame(105)：
   105 是 P帧2 的第一个包 → depacketizer 保证 is_first_packet_in_frame = true
   → 触发条件 ① 直接成立 ✓（根本不看 104/103）
106/107 到达 → prev 存在、seq 连续、timestamp 相同、prev.continuous → 触发 ✓
107 M=1 → FindFrames 从 107 往回搜 → 106 → 105（首包）→ P帧2 完整组出
```

每帧第一个包必带首包标记（单 NAL/STAP-A/FU-A 首片都置位），触发条件 ① 不依赖前一帧；组帧往回搜只搜**本帧范围**。**PacketBuffer 只做帧内完整性，不查缺失包。**

**NackRequester 层（6.1）——103 的归宿**

```
103 缺失 → 进 nack_list_ → 发 NACK 向对端要 103（包级自救）
103 在 PacketBuffer 超时前赶回 → P帧1 补组出来
赶不上 → P帧1 丢弃（这是 NACK 的事，不影响 P帧2）
```

**FrameBuffer2 层（M96 客户端，课程线不实现）——"P帧2 不出帧"在这里**

```
P帧2 组出 → InsertFrame → PropagateContinuity：帧 id 必须连续
   P帧1 缺 → 帧序列断裂 → P帧2 不连续
→ 非关键帧 + 不连续 → 不立即出帧，进入等待
→ 等待超时 → keyframe_required_ 置位 → 只放行关键帧，等新 IDR 才恢复
```

**"不出帧"的判断靠帧连续性 + 关键帧需求，不靠查缺失包 set。**

| 层 | 职责 | 对 P帧2 | 对 103 |
|----|------|--------|--------|
| **PacketBuffer**（5.3~5.5） | 帧内完整性 | 正常组帧吐出 | 不管 |
| **NackRequester**（6.1） | 缺失包重传 | 不管 | nack_list_ → NACK 要包 |
| **FrameBuffer2**（M96 客户端） | 帧间完整性 | 序列断裂 → 不出帧 → 超时等关键帧 | 不管（看"帧有没有"，不看"包缺没缺"） |

> 一句话：**缺失包 set（nack_list_）只管重传；"不出帧"靠帧连续性 + 关键帧需求，不是查缺失集合。**

## 四、一句话记忆

> **帧内完整性靠 PacketBuffer 的"等齐再吐"：环形 vector 按 seq 取模存放，continuous 字段可传递地标记"前面全连续"，首包到达或前包连续两个条件触发检测，经 seq 紧邻、同 timestamp 两道闸门后从末包往回搜组帧；帧间完整性靠参考链判断——关键帧独立可解，P 帧依赖前一帧，断链就丢到下一个关键帧为止（或 PLI 主动要）。**
