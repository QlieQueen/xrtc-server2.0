# v2_6.5 RTX 配置接入与 SSRC 分流

> 状态：代码课笔记（2026-08-17），6.5 配置接线完成 + 服务端 GDB 联调验证
> 定位：6.4 立了 `RtxReceiveStream` 类框架，这一课**把 RTX 配置从 SDP 提取出来、接进接收流、按 SSRC 把 RTX 包分流到 RtxReceiveStream**——RTX 链路在接收侧"通电"
> 参考：RFC 4588、`session_description.{h,cpp}`、`peer_connection.cpp:CreateVideoReceiveStream`
> 配套：`v2_6.4-RTX重传接收与包恢复.md`（RTX 协议 + RtxReceiveStream 框架）、`v2_6.2-RTCP-NACK报文格式.md`（NACK 报文）

## 一、这一课做什么

6.4 的 `RtxReceiveStream` 是孤立的类（没接入）。它要工作，需要三样东西喂进来：

1. **rtx_ssrc**：RTX 通道的 SSRC（识别"这包是 RTX 通道的"）
2. **rtx_associated_payload_types**：`map<rtx_PT, 媒体_PT>`（恢复时把 PT 换回去）
3. **media_sink**：恢复后的包喂回 `RtpVideoStreamReceiver`（6.6 恢复实现用）

这三样全都来自 **SDP 协商**。6.5 就是把它们从 `video_content` 提取出来、一路传进 `VideoReceiveStream`，并在 `OnRtpPacket` 入口按 SSRC 分流。

## 二、数据流

```
远端 SDP (offer)
  ├── a=rtpmap:99 rtx/90000 + a=fmtp:99 apt=107   →  rtx_PT=99, 媒体_PT=107
  ├── a=ssrc-group:FID 1087136548 1670862632       →  主SSRC=1087136548, RTX_SSRC=1670862632
  │
  ▼
CreateVideoReceiveStream(video_content)
  ├── config.rtp.remote_ssrc = remote_video_ssrc_          ← 已有
  ├── config.rtp.rtx_ssrc = remote_video_rtx_ssrc_         ← 6.5 新增
  └── config.rtp.rtx_associated_payload_types[99] = 107    ← 6.5 新增
  │
  ▼
VideoReceiveStream 构造
  ├── rtx_ssrc != 0 → 创建 RtxReceiveStream(media_sink, media_ssrc, map, stat)
  │
  ▼
VideoReceiveStream::OnRtpPacket(包)
  ├── Ssrc == rtx_ssrc ? ──是──→ rtx_receive_stream_->OnRtpPacket(包)   ← RTX 包走这里
  └── 否则 ────────────────→ rtp_video_stream_receiver_.OnRtpPacket(包) ← 正常媒体包
```

## 三、提取逻辑（peer_connection.cpp）

```cpp
config.rtp.rtx_ssrc = remote_video_rtx_ssrc_;       // FID 组第二个 SSRC（前面已有）
for (auto codec : video_content->codecs()) {        // 遍历 codecs，找有 apt 的（rtx codec）
    auto it = codec->codec_param.find("apt");
    if (it != codec->codec_param.end()) {
        config.rtp.rtx_associated_payload_types[codec->id] = std::stoi(it->second);
        // rtx_PT(99) → 媒体_PT(107)
    }
}
```

关键点：
- **识别 rtx codec 靠 `apt` 参数**：普通媒体 codec（H264）没有 apt，rtx codec 才有 `apt=<媒体PT>`。所以"有 apt 的 codec 就是 rtx 通道"。
- `rtx_associated_payload_types` 是 map，天然支持多路 rtx 通道（多个媒体 PT 各配一路 rtx）。
- 用 `std::stoi` 把 apt 字符串转 int（比 C 的 `std::atoi` 更 C++，免 include `<cstdlib>`）。

## 四、SSRC 分流设计（video_receive_stream.cpp）

```cpp
void VideoReceiveStream::OnRtpPacket(const webrtc::RtpPacketReceived& packet) {
    if (rtx_receive_stream_ && packet.Ssrc() == config_.rtp.rtx_ssrc) {
        rtx_receive_stream_->OnRtpPacket(packet);      // RTX 包 → 恢复流
    } else {
        rtp_video_stream_receiver_.OnRtpPacket(packet); // 媒体包 → 正常接收流
    }
}
```

**两层识别各司其职**：

| 层 | 依据 | 作用 |
|----|------|------|
| **外层**（VideoReceiveStream） | **SSRC** == rtx_ssrc | 分流：RTX 包进 RtxReceiveStream，媒体包进主接收流 |
| **内层**（RtxReceiveStream，6.6） | **PT** 查 rtx_associated_payload_types_ | 恢复：拿媒体 PT、读 OSN 还原原序号 |

为什么外层用 SSRC 不用 PT？——联调实验证明（6.3）：**客户端按协商值重传，rtx PT 可能变（offer 改 108 就发 108），但 RTX SSRC 稳定**。SSRC 分流更可靠。

> 细节：`rtx_receive_stream_ &&` 防御——`rtx_ssrc==0`（对方没开 RTX）时不建流，条件短路避免空指针。实际 RTP SSRC 不会是 0，但防御性写法更稳。

## 五、联调验证（服务端 GDB 断点）

在 `CreateVideoReceiveStream` 的 `make_unique<VideoReceiveStream>(config)` 处断点，打印 config：

```
(gdb) p config
$1 = { el = ..., clock = ..., rtp = {
    local_ssrc = 1,
    remote_ssrc = 1087136548,
    rtx_ssrc = 1670862632,
    rtx_associated_payload_types = std::map with 1 element = {[99] = 107}
  }, ...}
```

对照线上 SDP 逐项核对，全部一致：

| 配置字段 | 提取值 | SDP 来源 | ✓ |
|---|---|---|---|
| `remote_ssrc` | 1087136548 | `a=ssrc-group:FID 1087136548 1670862632` 第一个 | ✅ |
| `rtx_ssrc` | 1670862632 | FID 组第二个 | ✅ |
| `rtx_associated_payload_types` | `{[99]=107}` | `a=rtpmap:99 rtx` + `a=fmtp:99 apt=107` | ✅ |

配置提取链路完全打通。

## 六、与 6.6 的衔接

6.5 后，RTX 包已经能正确分流到 `RtxReceiveStream::OnRtpPacket`。但该方法还是空的——**6.6 填充恢复逻辑**（读 OSN → 还原 seq/PT/SSRC → 去 OSN → recovered → 喂回 media_sink），届时 `parsing rtp payload failed` 噪声消失、`recovered_list_`（6.1 预留）生效，NACK 闭环完整。

## 七、一句话记忆

> **6.5 = 让 RtxReceiveStream "通电"**：从 SDP 提取三样（rtx_ssrc / rtx_PT→媒体_PT 映射 / media_sink）一路传进接收流，`OnRtpPacket` 按 **SSRC** 分流——RTX 包进 RtxReceiveStream，媒体包进主接收流。识别 rtx codec 靠 **apt 参数**（有 apt 就是 rtx 通道）。外层 SSRC 分流（稳）、内层 PT 查表（恢复），两层各司其职。
