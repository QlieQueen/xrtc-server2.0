> 定位：理论铺垫。6.1 起逐课实现：NackRequester → RTCP NACK 通道 → RTX 接收 → RTX 解封装
> 配套：Phase 3 已具备 RTT 测量（RR 的 LSR/DLSR，4.12~4.15）、RTCP 发送链路（4.17 观察者闭环）

## 一、为什么需要 NACK？与 ACK 有什么不同？

### 为什么需要

- RTP 跑在 **UDP** 上：无重传、无确认、丢包难免（拥塞丢弃/路由抖动）
- 丢包对视频的杀伤：一帧的包缺一个 → **帧组不齐 → 解码失败** → 花屏卡顿
- 恢复手段：**重传**（发送方把丢的包再发一次），这是成本最低的丢包恢复
- 但 UDP 本身不带重传 → 接收方必须**告诉发送方"你丢了哪个包"** → 这就是 NACK

### NACK vs ACK（TCP）

| | ACK（TCP） | NACK（RTP/RTCP） |
|---|---|---|
| 反馈对象 | **每个包**都确认 | **只有丢的包**才反馈 |
| 反馈量 | 大（全量确认） | 小（只报缺失） |
| 发送方状态 | 明确知道每个包的状态 | 只知道"被点名"的丢了 |
| 适用 | 可靠传输、带宽不敏感 | 实时媒体、带宽宝贵 |

**为什么 RTP 选 NACK 不选 ACK**：

1. **带宽不对称**：视频下行带宽宝贵，每个包回一个确认 = 反向流量放大，还要占用网络资源
2. **实时流容忍"个别丢失"**：视频不像文件传输"一个都不能少"——丢了可以重传，**重传不到就放弃，等下一关键帧恢复**，不追求 100% 可靠
3. ACK 的可靠性依赖"全量确认"，NACK 的可靠性依赖发送方的"重传 + 放弃策略"

一句话：**收到的不说话，丢的才说话**。类比：ACK 像每封信都要回执，NACK 像只有信丢了才打电话。

## 二、NACK 基本流程

```
推流端(发送方)                                 SFU(接收方)
    │                                             │
    │ ─────── RTP seq=100 ─────────────────────► │
    │ ─────── RTP seq=101 ─────────────────────► │
    │ ─────── RTP seq=102 ─────────────────────► │
    │ ─────── RTP seq=103 ────── 丢包 ✗ ──────── │
    │ ─────── RTP seq=104 ─────────────────────► │
    │                                             │ ① 检测缺失: 104 到了, 103 还没到
    │ ◄────── RTCP NACK (请求重传 103) ───────── │ ② 发 NACK, 列出缺失 seq
    │ ③ 从重传缓存里找到 103                        │
    │ ─────── RTP 重传 seq=103 ────────────────► │ ④ 收到重传, 标记 recovered, 帧补齐
```

五步：

1. **检测缺失**：接收方发现序号不连续（期望 103，却先到 104）
2. **发 NACK**：RTCP NACK 报文，带上缺失包的 seq 列表（一个 NACK 可点名多个包）
3. **查重传缓存**：发送方必须**保留最近一段时间发出的包**（重传缓冲区），否则想重传没得传
4. **重传**：把对应包重新发出（RTP 头不变，只是再发一次）
5. **补齐**：接收方收到重传包，标 `recovered`（统计时不计入丢包率），帧完整可组帧

关键前提：**发送方要有重传缓存**（WebRTC 里是 RtpSender 的发送缓存，存最近 ~1s 的包）。

## 三、四个关键问题

### 1. 什么时候触发 NACK？

不是"发现缺失就立即发"，要分两步看：

- **记账**：维护缺失包集合（如 `missing_packets_` / `nack_list_`）。收到 seq=104 时，把 103 记入缺失
- **触发**：到触发时机，把缺失集合打包成 NACK 发出。触发时机由**乱序判断**决定（见问题 4）——先给乱序包一个到达窗口，窗口内到了就从缺失集合删除（不 NACK），窗口过了还在才 NACK

WebRTC 的 NackRequester：收到包更新缺失集合 + **乱序直方图**，定时器/事件驱动发 NACK 列表。

### 2. 重传包可能还会丢：两次重传间隔怎么控制？

核心原则：**重传间隔 ≥ RTT**。

- 第一次重传发出后，至少一个 RTT 才能到达；如果间隔 < RTT，第一次还没到就发第二次 → 白费带宽，可能制造更多拥塞
- 所以间隔要**基于 RTT 自适应**：1×RTT、2×RTT、4×RTT… 指数退避（和 TCP 超时重传一个思路）
- RTT 从哪来？**RTCP RR 的 LSR/DLSR 算**（Phase 3 的 4.12~4.15 已实现！）——这是 NACK 依赖 RTT 的原因，也是课程顺序安排的原因
- 同时限重传次数（如最多 2~3 次），防止无限重传

### 3. 重传一直不成功怎么办？

**放弃**。实时媒体是"及时性优先"：

- 设上限：重传次数上限（如 3 次）/ 时间上限（如几百 ms），超过就放弃这个包
- 为什么能放弃：单个包丢了 → 最多丢这一帧；等**下一关键帧**画面就恢复。死等一个包反而让延迟无限增大
- 帧组不齐的后果链条：该帧不出帧 → 持续缺帧 → 缓冲积压/清空 → **请求关键帧（PLI）**彻底重置——这是 8.x 的 PLI 要解决的问题

一句话：**NACK 负责"尽力补"，PLI 负责"补不回来就重开"**。

### 4. 乱序 vs 丢包：怎么区分？乱序有什么优化？

**乱序 ≠ 丢包**：乱序的包最终会到（只是绕了路），丢包的包永远不来。把乱序当丢包处理 = 白白重传、浪费带宽、甚至加剧拥塞。

优化手段（WebRTC NackRequester 的做法）：

1. **等待窗口**：发现缺失先不 NACK，等一小段时间（10~30ms 量级），乱序包大概率在此期间到达
2. **乱序直方图（reordered_histogram_）**：统计"包到达时相对期望序号的偏移分布"——记录网络乱序的严重程度。乱序严重 → 等待窗口调大；乱序稀少 → 窗口调小。**自适应**，不乱配死值
3. 窗口过了还没到 → 判定为真丢包 → 进 NACK 流程

判断顺序：**记账缺失 → 等窗口（排除乱序）→ 超时未到才 NACK → 重传间隔按 RTT 退避 → 超限放弃 → 下一关键帧兜底**。

## 五、一句话记忆

> **NACK = 收到的不说话、丢的才说话**（对比 ACK 全量确认，省带宽、符合实时流的容忍度）；流程 = 检测缺失 → RTCP NACK 点名 → 发送方查重传缓存重发 → 接收方标 recovered 补齐；四个关键控制：**乱序等待窗口（直方图自适应）→ 超过才 NACK → 重传间隔 ≥ RTT 指数退避 → 超限放弃、靠 PLI 关键帧兜底**；前提是发送方必须留重传缓存。
