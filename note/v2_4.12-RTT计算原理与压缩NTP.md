## 一、RTT 是什么：用 SR/RR 测一次往返

RTT（Round-Trip Time）是媒体路径往返延迟，是衡量传输质量、调整码率/拥塞控制的根本指标。RTCP 的 **SR + RR 报告块** 就是为了测它而生的：SR 是"我发了多少"，RR 报告块里带 **LSR / DLSR** 两个字段，让对端能算出一趟往返的时间。

## 二、四时间戳模型（RFC 3550）—— RTT 的物理意义

```
发送端(A)                    接收端(B)
   │                           │
   │── SR ────────────────────►│
   │  T1: SR发出时刻           │  T2: SR到达时刻
   │                           │
   │◄────── RR ────────────────│
   │  T4: RR到达时刻           │  T3: RR发出时刻
```

- **T1**：A 发出 SR 的时刻（A 的墙上时钟）
- **T2**：B 收到 SR 的时刻（B 的墙上时钟）
- **T3**：B 发出 RR 的时刻（B 的墙上时钟）
- **T4**：A 收到 RR 的时刻（A 的墙上时钟）

一趟往返总耗时 = 上行 `T2−T1` + 下行 `T4−T3`：

```
RTT = (T4 − T3) + (T2 − T1)
```

**关键陷阱**：`(T4−T3)`、`(T2−T1)` 单看是**垃圾数字**——它们跨越两个端，而两端墙上时钟不同步（任意偏置）。但**同端相减**的项才是干净的。改写：

```
RTT = (T4 − T3) + (T2 − T1)
    = T4 − T3 + T2 − T1
    = T4 − (T3 − T2) − T1          ← T3−T2 是 B 端自收 SR 到发 RR 的延迟
    = T4 − LSR − DLSR
```

- **LSR（Last SR）** = T1：SR 里的 NTP 时间戳，B 收到 SR 后**原样抄**进自己 RR 报告块
- **DLSR（Delay Since Last SR）** = T3 − T2：B 收 SR → 发 RR 的停留时间
- **A** = T4：A 收到 RR 时的本地时刻

> 三个量里，LSR 来自 A 自己的时钟（SR 里写的），A 和 LSR 是**同端相减**（抵消 A 的钟偏）；DLSR 是 B 端**自产自销**（内部停留时间，与 A 的钟无关）。RTT 从此不含任何钟差。

## 三、完整 NTP：本质是一个 64 位整数

NTP 时间戳（1900 纪元）是 64 位：

```
┌───────────高32位───────────┐┌───────────低32位───────────┐
│          秒数 (整数)         ││      小数 × 2³² (整数)      │
│       0 ~ 2³²-1 秒          ││  每个单位 = 1/2³² 秒 ≈ 0.23ns │
└────────────────────────────┘└────────────────────────────┘
```

**不要把它想成"秒 + 小数点"**。它就是一个巨大的整数，计数单位是 **1/2³² 秒**：

```
完整NTP(64位) = 从1900年到现在过了多少个 1/2³² 秒
              = 秒数 × 2³² + 小数部分(整数)
```

例：`现在 = 200.5 秒` → 完整 NTP = `200.5 × 2³²`（一个没有小数点的整数）。

## 四、压缩 NTP：中间 32 位 = 换一把更粗的尺子

RR 报告块的 **LSR / DLSR 都是 32 位**，放不下完整 64 位 NTP，所以只取**中间 32 位**：

```cpp
// rtp_rtcp_impl.cpp GetFeedbackState
state.remote_sr = ((receive_ntp_secs & 0x0000FFFF) << 16) +   // 秒的低16位 → 高16位
                  ((receive_ntp_frac & 0xFFFF0000) >> 16);   // 小数的高16位 → 低16位
```

它干了什么？**除以 2¹⁶**：

```
sec[15:0] × 2¹⁶ + frac[31:16]  = (sec × 2³² + frac) / 2¹⁶  (取模 2³²)
                                = 完整 NTP ÷ 2¹⁶
```

| | 完整 NTP | 压缩 NTP |
|---|---|---|
| 单位 | 1/2³² 秒（≈0.23ns） | **1/2¹⁶ 秒（≈15.26μs）** |
| 表示范围 | 136 年 | 2³² × 1/2¹⁶ 秒 = **18.2 小时**（回绕） |
| 环绕处理 | —（136 年内不回绕） | **无符号减法（模 2³²）自动兜底**：真实差 < 18.2h 即无歧义（详见第八节） |

**一句话：压缩 = 把时间戳从"纳秒尺"换算到"1/2¹⁶ 秒尺"**（二进制除法砍掉低 16 位）。

## 五、压缩会丢精度吗？—— 丢，但丢的是没意义的位

丢的是小数部分的低 16 位（除法余数，最多 15 微秒）。例：

```
时刻 = 200.5 秒 + 小数 0.400001 秒
NTP 内:  0.400001 × 2³² ≈ 0x66666612   (分辨率 0.23ns)
取高16位: 0x6666 / 2¹⁶   = 0.399993 秒   (分辨率 15.26μs)

丢掉: 0.400001 − 0.399993 = 8 微秒
```

- "进度"的大致位置**保住了**（0.4 秒没变），只是内部的更细进度（微秒以内）被砍
- 系统时钟（`CurrentNtpTime`/`TimeMillis`）精度本身到不了纳秒级，丢掉的位**不含真信息**
- RTT 量级是毫秒，15 微秒误差不到 1%，无实质影响

**关键认知：这不是"为了省空间随便砍"，而是"除法换单位"——为的是和 DLSR 对齐到同一把尺子（见第七节）。**

## 六、LSR / DLSR 各自从哪来

### 6.1 LSR = 发送端 SR 里的 NTP，原样抄

```
推流端 SR ──NTP(64位)──► 收流端 HandleSr 存下
                             ↓ 压缩成中间32位 (GetFeedbackState)
                          remote_sr ──► report_block.SetLastSr(remote_sr)
```

LSR 是 **A 自己的时钟**写下的时刻（SR 发出的那瞬间），B 只是**抄写员**。

### 6.2 DLSR = 收 SR → 发 RR 的停留时间，本端自算

```cpp
// rtcp_sender.cpp CreateRtcpReportBlocks
int32_t now = webrtc::CompactNtp(clock_->CurrentNtpTime());   // A：发 RR 时，压缩 NTP
int32_t receive_time = feedback_state.last_rr_ntp_secs & 0x0000FFFF;
receive_time <<= 16;
receive_time += ((feedback_state.last_rr_ntp_frac & 0xFFFF0000) >> 16); // 收 SR 时，压缩 NTP
int32_t delay_since_last_sr = now - receive_time;             // T3 − T2

report_block.SetLastSr(feedback_state.remote_sr);             // LSR
report_block.SetDelayLastSr(delay_since_last_sr);             // DLSR
```

DLSR 的**单位天生就是 1/2¹⁶ 秒**（RFC 3550 写死：DLSR 以 1/65536 秒为单位）。`now` 和 `receive_time` 都是压缩 NTP（1/2¹⁶），相减结果自然也是 1/2¹⁶ 单位——**这就是"压缩"必须存在的根本理由**。

## 七、RTT = A − LSR − DLSR：三量必须同一把尺子

发送端收到 RR 后，读自己现在的时刻 A，算：

```
RTT = A − LSR − DLSR
```

**关键不是"都是 32 位"，而是"都是 1/2¹⁶ 秒单位"**——位数相同 ≠ 单位相同，单位不同照样减不了：

```
反例（单位不同，直接减是灾难）:
A   = 200.00 × 2³² = 858,993,459,200   (1/2³² 秒)
LSR = 199.50 × 2³² = 856,638,386,176   (1/2³² 秒)
DLSR = 0.05 × 2¹⁶ = 3,277              (1/2¹⁶ 秒)
A − LSR = 2,355,073,024；DLSR = 3,277；差 71 万倍，没法减

正例（三量统一到 1/2¹⁶ 秒）:
A   = CompactNtp(now)        = 200.00 × 2¹⁶ = 13,107,200
LSR = remote_sr（从SR压缩抄）  = 199.50 × 2¹⁶ = 13,074,432
DLSR = delay_since_last_sr    = 0.05 × 2¹⁶ = 3,277
RTT = 13,107,200 − 13,074,432 − 3,277 = 29,491 (1/2¹⁶ 秒) = 0.45s ✓
```

> LSR 是压缩 NTP（÷2¹⁶ 换到 1/2¹⁶ 尺），DLSR 天生 1/2¹⁶，**A 也必须用 `CompactNtp(now)` 换到同一把尺**。三者同单位，减法才干净。

## 八、三个坑（对端解析时务必注意）

1. **单位必须统一**：A/LSR/DLSR 三个量都要是 1/2¹⁶ 秒。A 不能直接拿完整 NTP 或秒数去减。
2. **回绕**：压缩 NTP 只有 18.2 小时范围，秒的低 16 位周期回绕。**注意：保护不来自 `CompactNtp`（它只管换单位），来自无符号减法（模 2³² 算术）**。
   - 32 位压缩 NTP 是一个**均匀计数器**：不区分"秒/分数"部分，每 1/2¹⁶ 秒 +1，数到 2³²−1 回 0（**里程表** 999999→000000）
   - **跨环绕点演算**：LSR = 65535.76 秒（计数 4,294,951,567，环绕前），A = 65536.01 秒（环绕后计数 655），真实 RTT = 0.25 秒：
     ```
     A' − LSR' = 655 − 4,294,951,567  (mod 2³²)
               = 655 + 15,729 = 16,384 tick = 0.25s ✓ 分毫不差
     ```
     模 2³² 自动"借用"环绕掉的一圈（`2³² − LSR'`），跨越环绕点的差照样精确
   - **前提**：真实差 Δ < 18.2 小时（= 2³² tick）。RTT 毫秒~秒级，6.5 万倍裕量，永远安全
   - **int32 陷阱**：代码用 `int32_t now/receive_time`，环绕前的大值存进去变成负数（4,294,951,567 → −15,729）。**位模式层面减法依然正确**（x86 溢出位与无符号相同）；但**绝不能拿有符号语义去解释中间值**（比较大小/判断正负）。差值只看位模式、转 uint32 落地，对端拿 uint32 解析，天然正确
3. **LSR/DLSR = 0 陷阱**：没收到过 SR 时，报告块这两个字段是 0。填的时候已用 `last_rr_ntp_secs/frac > 0` 判断；对端解析时同样不能拿 0 当有效值去算 RTT（会算出天文数字），要判 LSR > 0。

## 九、完整闭环（消息流）

```
推流端周期发 SR（含 NTP 时间戳 T1）
  → 收流端 HandleSr 解析，存 last_rr_ntp_secs/frac + remote_sr   (4.13/4.14)
  → 收流端周期发 RR，CreateRtcpReportBlocks:
        LSR = remote_sr（抄 SR 的 T1）
        DLSR = CompactNtp(now) − 收SR时刻（T3 − T2）             (4.12/4.15)
  → 推流端收到 RR，解析报告块，算:
        RTT = CompactNtp(now) − LSR − DLSR                      (对端视角，待落地)
```

**本端视角（已实现，4.12/4.15）**：`CreateRtcpReportBlocks` 填 LSR/DLSR——这是**制造 RTT 计算的原料**。
**对端视角（未实现）**：`HandleRr` 里解析 `report_block.last_sr()` / `delay_since_last_sr()`，用第七节公式算 RTT——这是**消费原料**。当前 `(void)sender` 仍未 Append 复合包，后续课程接通发送闭环后，RTT 就能真正算出来。
