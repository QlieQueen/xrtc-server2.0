## 七、kRtcpReport 身份辨析（读码讨论沉淀）

> 事后重读 RTCPSender 时梳理出的几个关键理解，曾在对话中反复绕，沉淀在此。

### 1. kRtcpReport 是"信号"不是"报文"

- 它只有一种来源：周期报告定时器 `TimeToSendRTCP()` → `SendRTCP(kRtcpReport)`
- 它不代表任何真实 RTCP 报文，真正发出去的报告是 `kRtcpSr`/`kRtcpRr`（由 `PrepareReport` 决定）
- `builders_` 里**没有** kRtcpReport 对应的构建函数——所以遍历时一定走 `could not build` 的 WARNING 分支

### 2. kCompound 模式的含义 = "无条件发报告"

`PrepareReport` 里 `(method_ == kCompound)` 直接短路为 true → 无条件 `SetFlag(kRtcpRr/Sr, true)`。因此：

| 模式 | 报告怎么发 | kRtcpReport 角色 |
|------|-----------|-----------------|
| kCompound | 每次 SendRTCP 都顺带 SR/RR（无论本次是 Report/PLI/NACK） | 摆设，进集合后被当 unknown 删掉 + 刷 WARNING |
| kReducedSize | `ConsumeFlag(kRtcpReport)` 消费一次才发一次（发完即删） | 关键决策者 |
| kOff | 不发 | — |

**"kCompound 下任何 RTCP 发送都自动带 SR/RR"成立；"靠携带 kRtcpReport 实现"不成立**——顺带报告是 kCompound 分支硬编码，与 kRtcpReport 无关。

### 3. PLI/NACK 也会被顺带报告

- `RequestPliCb` → `SendRTCP(kRtcpPli)`：PLI 也是周期定时发送（`request_pli_interval_ms`，8.x 配置）
- `SendNack()` → `SendRTCP(kRtcpNack)`：NACK 是事件触发（收到丢包才调）
- 两者在 kCompound 下都会合成 `{kRtcpPli, kRtcpRr}` / `{kRtcpNack, kRtcpRr}` 复合包

### 4. "常驻"的真相：每轮重生，不是 is_volatile=false

- 全工程所有 `SetFlag` 都是 `is_volatile=true`（最终版 v2_9.9 亦然），**没有一处用 false 做常驻标志**——`is_volatile=false` 是给 WebRTC 原版语义预留的死代码
- kRtcpReport 虽然 volatile、每轮被删，但周期定时器每 100ms 重新 `SetFlag`，所以"看起来常驻"，机制上却是"每轮重生"

### 5. 可观察副作用：kCompound 下每 100ms 刷一条 WARNING

```
could not build rtcp packet for packet type: 1   // kRtcpReport = 0x0001
```

无害但很吵。以后真跑起来看到这条日志不要困惑。严格说可优化（让 kRtcpReport 在 kCompound 下不 SetFlag 或自行消费），课程没做。
