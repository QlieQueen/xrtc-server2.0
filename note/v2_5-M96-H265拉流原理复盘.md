# v2_5 M96 H265 拉流原理复盘：SDP 协商 ≠ 编解码支持

> 状态：复盘笔记（2026-08-14 合并修订版，融入 Generic packetization 分层认知）
> 定位：把**用户 M96 实战**（改 SDP 让 H265 拉流 + 硬解渲染）和 **5.x 课程**（H264 depacketizer + PacketBuffer 组帧）焊在一起
> 结论一句话：**协商上 H265 ≠ WebRTC 支持 H265。你的 H265 是"披着 H265 名字、走 generic 通道"的字节搬运，解码全靠自己硬解。**
> 配套：`v2_5-视频帧与GOP背景知识.md`（帧/包/GOP、打包拆包镜像、FU-A 格式、E/M 位）

## 〇、分层认知模型：Codec / Payload Format / RTP 是三层

整个问题最终要建立的三层模型（本笔记最关键的概念锚点）：

```
                    Codec（H.264 / H.265 / VP8 ...）
                      │  决定"编码字节长什么样"
                      ▼
              Encoded Frame
                      │  决定"帧字节怎么装进 RTP"
                      ▼
             Payload Format（RFC 6184 / RFC 7798 / Generic ...）
                      │  决定"一个 RTP 包长什么样"
                      ▼
                     RTP
        ┌──────────────────────────────┐
        │ RTP Header                   │
        ├──────────────────────────────┤
        │ RTP Payload                  │
        │ RTP 本身不规定 payload 结构   │
        └──────────────────────────────┘
```

**核心：RTP 层不关心 H.264/H.265 的编码语义**。具体 codec 如何组织 RTP payload，是由对应的 RTP Payload Format 规定的：

```
RTP
 ├── H.264 Payload Format → RFC 6184（STAP-A / FU-A / Single NALU）
 ├── H.265 Payload Format → RFC 7798（AP / FU，M96 不支持）
 ├── Generic Payload Format → WebRTC 私有（1 字节头 + 帧片段）
 ├── VP8 / VP9 / AV1 ...
 └── 你自己的私有 Payload Format（封闭系统可行，无标准互操作）
```

## 一、核心问题（起）

> M96 既然不支持处理 H265 的 codec info，那应该也不支持 H265 的视频帧分片和组帧，为什么我通过改动底层 WebRTC 对 SDP 的处理，却可以完整实现 H265 拉流，然后硬解码出来并渲染？难道 H264 和 H265 的分片和组帧是一样的逻辑？

背景：用户在 M96 上改 SDP 处理，强行构造 H265 codec info，实现 Windows 客户端 H265 拉流（云手机方案）+ D3D11VA 硬解渲染。推流端是另一位离职同事做的，拉流端是用户依样画葫芦做出来的，协商居然通了。

## 二、真相：M96 根本不认识 H265，你走的是 generic 通道

### 2.1 三个关键代码证据

**证据 1：M96 没有 H265 的 depacketizer**

`modules/rtp_rtcp/source/` 下只有 `video_rtp_depacketizer_{av1,generic,h264,raw,vp8,vp9}.cc`——**没有 H265**。

**证据 2：codec 名字查表查不到 H265，自动落到 generic**

```cpp
// api/video_codecs/video_codec.cc:126
VideoCodecType PayloadStringToCodecType(const std::string& name) {
  if (name == kPayloadNameVp8)   return kVideoCodecVP8;
  if (name == kPayloadNameVp9)   return kVideoCodecVP9;
  if (name == kPayloadNameAv1)   return kVideoCodecAV1;
  if (name == kPayloadNameH264)  return kVideoCodecH264;
  if (name == kPayloadNameMultiplex) return kVideoCodecMultiplex;
  return kVideoCodecGeneric;   // ← "H265" 走到这里
}
```

**你不是手动设的 generic，是查表查不到自动 fallback 的。**

**证据 3：generic depacketizer 读 1 字节头后原样透传，不解析任何 NAL**

```cpp
// modules/rtp_rtcp/source/create_video_rtp_depacketizer.cc:27
switch (codec) {
  case kVideoCodecH264:  return make_unique<VideoRtpDepacketizerH264>();
  ...
  case kVideoCodecGeneric:
    return make_unique<VideoRtpDepacketizerGeneric>();  // ← H265 落这
}
```

```cpp
// video_rtp_depacketizer_generic.cc:37 Parse()
uint8_t generic_header = payload_data[0];          // 1 字节 generic 头
parsed->video_header.frame_type = (generic_header & kKeyFrameBit /*0x01*/)
                                      ? kVideoFrameKey : kVideoFrameDelta;
parsed->video_header.is_first_packet_in_frame = (generic_header & kFirstPacketBit /*0x02*/) != 0;
...
// 头之后：payload[1:] 原样透传 —— 不解析任何 NAL！
```

### 2.2 你的 H265 实际走的完整链路

```
① SDP 协商出 "H265/90000"（你改 SDP 让它进了 codec 列表）
② PayloadStringToCodecType("H265") → 查不到 → kVideoCodecGeneric
③ CreateVideoRtpDepacketizer(kVideoCodecGeneric) → VideoRtpDepacketizerGeneric
④ Generic::Parse()：读 1 字节 generic 头（2 bit 标记），payload 原样透传
⑤ PacketBuffer 组帧：只按 timestamp/seq/M 位（与编码格式无关）
⑥ 你拿到 codec_payload = H265 原始 NAL 数据
⑦ 你拼回 Annex B + 起始码 → 喂 D3D11VA 硬解
```

**底层始终没有"认识"H265，因为你的 H265 压根没让它解析。**

## 三、关键认知 1：SDP 协商只认名字，不看内部支持

你"竟然协商上了 H265！"的惊讶，藏着 WebRTC 的关键认知：

**SDP 协商只看名字匹配，不看 WebRTC 内部认不认这个 codec。**

```
推流端：SupportedH265Codecs() 返回格式名 "H265"   ← 同事改的
拉流端：SupportedH265Codecs() 返回格式名 "H265"   ← 你照葫芦画瓢
        ↓ 两边 SDP 一比对，payload type 一致
        ↓ 协商通过！"H265" 进了 m=video 行
```

协商成功只代表"双方同意这个 payload type 叫 H265"，**不代表 WebRTC 能编解码 H265**。协商之后 WebRTC 内部干了两件"装傻"的事：查表落 generic、收发管线全走 generic。

## 四、关键认知 2：generic 通道 = 带 2-bit 标签的字节搬运

### 4.1 为什么能跑通：切分可逆

generic 打包/拆包**完全不懂 NAL**，但能跑通，因为**切分是纯字节操作，完全可逆**：

```
发送端：把帧 F 切成 F1 | F2 | ... | Fn
接收端：按 seq 顺序拼回 F1 | F2 | ... | Fn = F
```

不需要理解内容，只要保证顺序和完整性就能还原——就像把一张纸剪成 5 段，按顺序贴回去就是原样。

### 4.2 generic 的对称性（关键前提）：收发两端必须同一种 Payload Format

**真正的原则不是"帧级切片错误，NALU 级切片正确"，而是：发送端和接收端必须使用同一种 RTP Payload Format。**

```
Generic Sender ↔ Generic Depacketizer   → 可以工作 ✓（你的 H265）
Generic Sender ↔ H264 Depacketizer      → 才会出问题 ✗（格式错位）
```

注意 generic 拆包会把 payload[0] 吃掉当 generic 头（数据从 payload[1] 透传）。所以**收发两端必须都用 generic**：

```
推流端：RtpPacketizerGeneric（BuildHeader 写入同样 2 个 bit）← 同事做的
拉流端：VideoRtpDepacketizerGeneric（读这 2 个 bit）        ← 你对称做的
```

你"拉流端就是学推流端做的"——收发对称，所以数据错位不了，跑通了。

### 4.3 generic 头：每包 1 字节，不是 100% 黑盒

严格说 generic **不是**"完全不透明的纯字节搬运"——每个 RTP 包 payload 开头有 1 字节 generic 头，只有 2 个 bit 有效：

```
RTP payload = [generic header 1字节][编码帧片段 bytes...]
                 ├─ bit0 (0x01) key frame 标记
                 └─ bit1 (0x02) 帧首包标记（每帧第 1 个包才置位）
```

**Packetizer 侧**（`rtp_format_video_generic.cc`，M96 收发对称的另一半）：

```cpp
// BuildHeader(): header_size_ = 1; 头字节构造
header_[0] = RtpFormatVideoGeneric::kFirstPacketBit;      // 0x02 帧首包
if (frame_type == kVideoFrameKey)
    header_[0] |= RtpFormatVideoGeneric::kKeyFrameBit;    // 0x01 关键帧
// 有 picture_id 时再加 0x04 + 2 字节扩展头（普通情况没有）

// NextPacket(): 每包先拷 header 再拷数据
memcpy(out_ptr, header_, header_size_);
header_[0] &= ~kFirstPacketBit;   // 第 2 包起清掉帧首位
memcpy(out_ptr + header_size_, remaining_payload_.data(), ...);
```

**这 2 个 bit 不是可有可无的装饰**：
- `bit1 帧首` + RTP 头的 `M 位帧尾` —— 一帧的首尾都标了，接收端组帧边界才完整
- `bit0 关键帧` —— 接收端丢帧/等关键帧策略靠它（丢包后要等关键帧才能恢复画面）

所以准确的说法是：**"带 2-bit 标签的透明搬运"**，而不是"纯 opaque 黑盒"。

### 4.4 底层怎么知道是 H265？—— 根本不知道

- **分片/组帧**：靠 RTP 头通用字段（timestamp/seq/M 位）+ generic 头 2 bit，与 H265 格式无关
- **NAL 结构识别、起始码、切片**：全是下游硬解封装自己做的，WebRTC 全程没参与
- 这就是"M96 不支持 H265 codec info 也能完整拉流"的原因——generic 通道里根本没有需要理解 H265 的解析逻辑，数据原样穿过

## 五、关键认知 3：帧 vs NAL——两种打包粒度

### 5.1 重新锚定两个词

- **帧** = 一**幅画面**。你眼睛看到的每一张图就是一帧。
- **NAL** = 组成这幅画面的**零件**。H264 里 SPS、PPS、IDR slice 都是 NAL。

```
一帧 = [S P S][ P P S][IDR slice..................]
      └零件1 ┘└ 零件2 ┘└──────    零件3  ──────────┘
帧 = 一袋零件
```

### 5.2 三条打包路线

| 打包路线 | 谁在用 | 切法 | 聚合 | 分片 |
|---------|--------|------|------|------|
| **generic** | 你的 M96 H265 | **整帧切**，不分零件，包边界随便 | 无 | 无 |
| **标准 H264** (RFC 6184) | 你 5.1 学的 depacketizer | **按零件切**，包边界 = NAL 边界 | SPS/PPS → STAP-A | IDR → FU-A |
| **标准 H265** (RFC 7798) | 标准 WebRTC（M96 没有） | **按零件切**，包边界 = NAL 边界 | VPS/SPS/PPS → AP | IDR → FU |

标准 H264 和标准 H265 的"按零件切"思路**完全对称**——小的聚合、大的分片。你学的 STAP-A/FU-A 是 H264 版，H265 标准版叫 AP/FU，结构几乎一样。

### 5.3 generic vs 标准对比

| | generic（你的 H265） | 标准 H264（FU-A） |
|---|---|---|
| **切分粒度** | 帧级（整帧切） | NAL 级（单 NALU 切） |
| **帧边界标记** | generic 头 bit1（帧首）+ M 位（帧尾） | depacketizer 解析 NAL 结构 + M 位 |
| **关键帧判断** | generic 头 bit0（0x01） | depacketizer 读 NAL type（IDR=5） |
| **对 NAL 的理解** | 不需要（解码器自己切） | 需要（包边界 = NAL 边界） |
| **丢 1 包的损失** | 帧拼不回，整帧丢（丢 SPS/PPS 时解码器状态也受影响） | 帧也拼不回，但 SPS/PPS 独立成包不会跟着丢；NACK 重传粒度可精确到 NAL |

> 注：两种粒度丢 1 个媒体分片都会导致整帧无法解码，**差异不是"标准能出图、generic 不能"**，而是：标准格式下 SPS/PPS 等关键零件独立成包（存活率高）、重传/丢帧策略可以精确到 NAL 级。

## 六、H264 标准打包完整流程（从打包到组帧）

```
一帧 = [SPS][PPS][IDR slice.........好大一块.........]
       └────────────────────────────────────────────────┐
包1 = STAP-A{SPS, PPS}   ← 两个小零件聚合装一包
包2 = FU-A{ IDR 第1片 }  ← IDR 太大切成3片，每片一包
包3 = FU-A{ IDR 第2片 }
包4 = FU-A{ IDR 第3片 }(M=1) ← 帧的最后一片
       └────────────────────────────────────────────────┘

接收端拆包（depacketizer）：
  包1 → 拆出 SPS、PPS 两个完整 NAL
  包2/3/4 → 3 片拼回一个完整 IDR NAL（首片重建 NAL 头）
  → 帧 = SPS + PPS + IDR，跟发送端一模一样
```

关键规则就一条：**一个包要么装"完整的零件"（单 NAL/STAP-A），要么装"同一个零件的几片"（FU-A）。绝不把两个不同 NAL 的各一半混进一个包。**

对比 generic：**包边界随便切**，可能切在 SPS 中间——但接收端按顺序拼回，纯字节拼接可逆，仍得到完整帧。

## 七、那 H264 Packetizer 的优势到底是什么？

Generic 在双方都是自己实现、Codec 固定的封闭 P2P 场景下完全够用，**"没有 H264 Packetizer 就不能传 H264"是错的**。H264 Packetizer 的真正优势有三：

### ① 保留 NALU 结构

RTP 层知道：这个包属于哪个 NALU、NALU 是什么类型（SPS/PPS/IDR）、是否被分片（FU-A）。

### ② 标准互操作性

RFC 6184 是标准，**任何实现 RFC 6184 的 RTP 接收端**（Chrome/Firefox/第三方 WebRTC）都能理解 STAP-A/FU-A/Single NALU。Generic 是 WebRTC 私有格式，没有这种互操作性——所以"自己定义私有格式"只在封闭系统可行，要对接第三方就必须走标准 Payload Format。

### ③ codec-aware 能力

中间设备、SFU 可以利用 NALU 结构做精细处理（识别关键帧、选择性转发 SPS/PPS、丢帧策略）。Generic 只能看到"带 2-bit 标签的字节流"。

## 八、分工：传输层搬"帧"，解码器切"零件"

```
WebRTC（generic）：只负责"把一帧字节完整搬到对面"  ← 不懂 NAL，没关系
你接的硬解：      拿到完整帧，自己按起始码切 NAL、解码 ← 它懂 NAL
```

分工极其干净：**传输层只搬运"帧"，NAL 解析是解码器的事。** 这就是为什么 generic 不需要懂 NAL 也能跑通。

## 九、最终三个结论

### 结论 1：RTP 本身不关心 codec 的编码语义

具体 codec 如何组织 RTP payload，由对应的 RTP Payload Format 规定（RFC 6184 做的事就是"定义 H264 如何作为 RTP payload 被封装"，不是 RTP 定义 H264）。

### 结论 2：Generic 可以传输任意 encoded frame，不需要理解 codec

只要收发两端协议一致（Generic ↔ Generic），就能把任意 codec 的完整帧搬过去。它带 1 字节标签（帧首 + 关键帧标记），不是纯黑盒，但足够透明。

### 结论 3：M96 上"没有 H265 codec 类型，却能稳定传 H265"完全解释通了

```
H265 Encoder → kVideoCodecGeneric → Generic Packetizer → RTP
              → Generic Depacketizer → 完整 H265 frame → 你的硬解
```

当时真正让 H.265 跑起来的关键，不是 M96 "支持了 H.265 RTP packetization"，而是：

> **绕过了 H.265-specific packetization，利用 generic 通道把完整 H.265 encoded frame 可靠地从一端搬到另一端。**

## 十、一句话记忆

> **协商上 H265 ≠ 支持 H265——查表查不到自动落 generic，带 2-bit 标签原样透传搬帧，解码全靠自给自足；SDP 名字只是门牌，门牌后面走的是不认识 H265 的通道。帧 = 一袋零件（NAL）：generic 整袋切，标准 H264/H265 按零件切（小聚合、大分片）。核心原则不是"帧级切错、NAL 级切对"，而是收发两端必须用同一种 Payload Format；H264 Packetizer 的优势是 NALU 保留 + 标准互操作 + codec-aware。**
