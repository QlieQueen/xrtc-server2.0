## 二、数据流全链路：一个 RTP 包从进来到吐出完整帧

```
线上 RTP 包（UDP 收到的字节流 Parse 出来）
→ RtpPacketReceived       线上一个包 = 一个对象（头字段 + 载荷 + recovered 标记）
→ VideoRtpDepacketizer::Parse → ParsedRtpPayload    ← 5.1 的解析
     ├─ video_payload   剥离打包格式后的编码数据（FU-A 拼回 NAL）
     └─ video_header    载荷元数据（codec/帧类型/首包标记/nalus）
→ OnReceivedPayloadData
→ PacketBuffer::Packet   缓冲单元（只拷 RTP 头字段 + video_header）
→ PacketBuffer::InsertPacket   环形缓冲 + 组帧（5.2 理论的实现）
→ InsertResult
     ├─ packets        一个或多个完整帧的包集合（按序，帧边界靠首包标记切）
     └─ buffer_cleared  缓冲被清过 → 该请求关键帧（8.x 前奏）
→ OnInsertedPacket      当前空体；5.5 在这里切帧 → RtpFrameObject
```

## 三、对象字典：每个类/结构体代表什么

| 对象 | 代表什么 | 关键点 |
|------|---------|--------|
| `RtpPacketReceived` | **线上来的一个包** | 解析好的 SSRC/seq/timestamp/M 位/PT + payload + `recovered()`（是否 RTX 恢复的） |
| `ParsedRtpPayload` | **depacketizer 的解析产物**（临时中转） | 两个成员：video_payload + video_header；Parse 完拆开传下去就没了 |
| `RTPVideoHeader` | **载荷的元数据** | codec/frame_type/width/height/is_first/is_last_packet_in_frame/video_type_header（H264 时是 nalus 数组）。**不上线**，内部传递 |
| `PacketBuffer::Packet` | **缓冲里的一个包**（环形 vector 的元素） | 构造只拷 RTP 头字段 + video_header；**video_payload 没填**（见 5.5）；另有 continuous（连续标记）、times_nacked |
| `PacketBuffer` | **乱序缓存 + 组帧器** | 环形 vector（512 起动态扩容至 2048，2 的幂）；InsertPacket 唯一入口 |
| `InsertResult` | **"这次插入触发了什么"** | packets = 完整帧的包集合（**不是帧对象**，可能含连续多帧，首包标记切帧界）；buffer_cleared = 缓冲被清，该要关键帧 |
| `RtpRtcpImpl` | Phase 2/3 的 RTCP 模块 | SetRemoteSsrc 过滤对端 SR |

## 四、关键代码注释版

### 4.1 OnReceivedPayloadData（5.3 我们写的）

```cpp
void RtpVideoStreamReceiver::OnReceivedPayloadData(
        rtc::CopyOnWriteBuffer codec_payload,        // ← 传了但没用！见 5.5
        const webrtc::RtpPacketReceived& rtp_packet, // 线上包（本课只用它的 Marker()）
        const webrtc::RTPVideoHeader& video)         // depacketizer 解析出的元数据
{
    // 把"线上包"变成"缓冲单元"：只拷 RTP 头字段 + video_header
    auto packet = std::make_unique<webrtc::video_coding::PacketBuffer::Packet>(
            rtp_packet, video);

    // H264 的 depacketizer 不填 is_last_packet_in_frame（E 位是 NAL 级边界）
    // 帧尾必须靠 RTP 头 M 位补 —— FindFrames 触发组帧的依据
    webrtc::RTPVideoHeader& video_header = packet->video_header;
    video_header.is_last_packet_in_frame |= rtp_packet.Marker();

    // 进缓冲组帧；结果（完整帧的包集合）交给 OnInsertedPacket
    OnInsertedPacket(packet_buffer_->InsertPacket(std::move(packet)));
}
```

### 4.3 InsertPacket（rtcbase）—— 插入 + 触发组帧

```cpp
PacketBuffer::InsertResult PacketBuffer::InsertPacket(
    std::unique_ptr<PacketBuffer::Packet> packet) {
  PacketBuffer::InsertResult result;
  uint16_t seq_num = packet->seq_num;
  size_t index = seq_num % buffer_.size();          // 环形槽位映射

  if (!first_packet_received_) {                    // 第一个包：记录起点
    first_seq_num_ = seq_num;
    first_packet_received_ = true;
  } else if (AheadOf(first_seq_num_, seq_num)) {    // 早于起点的包
    if (is_cleared_to_first_seq_num_) return result; // 已清理过的旧包：静默忽略
    first_seq_num_ = seq_num;                        // 否则重置起点
  }

  if (buffer_[index] != nullptr) {                  // 槽位被占
    if (buffer_[index]->seq_num == packet->seq_num) return result; // 重复包：丢弃
    while (ExpandBufferSize() && buffer_[seq_num % buffer_.size()] != nullptr) {}
    index = seq_num % buffer_.size();               // 扩容后重算槽位
    if (buffer_[index] != nullptr) {                // 2048 满了还冲突
      RTC_LOG(LS_WARNING) << "Clear PacketBuffer and request key frame.";
      ClearInternal();                              // 清空整个缓冲
      result.buffer_cleared = true;                 // 置位：该请求关键帧
      return result;
    }
  }

  packet->continuous = false;
  buffer_[index] = std::move(packet);               // 入槽
  UpdateMissingPackets(seq_num);                    // 记账缺失包（NACK 用）
  result.packets = FindFrames(seq_num);             // 组帧（识别完整帧）
  return result;
}
```

### 4.4 PotentialNewFrame（rtcbase）—— 两触发 + 三闸门（5.2 理论落地）

```cpp
bool PacketBuffer::PotentialNewFrame(uint16_t seq_num) const {
  size_t index = seq_num % buffer_.size();
  int prev_index = index > 0 ? index - 1 : buffer_.size() - 1;
  const auto& entry = buffer_[index];
  const auto& prev_entry = buffer_[prev_index];

  if (entry == nullptr)                  return false;
  if (entry->seq_num != seq_num)         return false;   // 槽位被环回旧包占着
  if (entry->is_first_packet_in_frame()) return true;    // 触发① 收到帧首包
  if (prev_entry == nullptr)             return false;
  if (prev_entry->seq_num != static_cast<uint16_t>(entry->seq_num - 1))
                                         return false;   // 闸1 seq 必须紧邻（防环形槽位冲突）
  if (prev_entry->timestamp != entry->timestamp)
                                         return false;   // 闸2 必须同帧（timestamp = 帧边界）
  if (prev_entry->continuous)            return true;    // 触发② 前面全连续
  return false;
}
```

### 4.5 FindFrames（rtcbase）—— 组帧四件事

```cpp
std::vector<std::unique_ptr<Packet>> PacketBuffer::FindFrames(uint16_t seq_num) {
  for (i < buffer_.size() && PotentialNewFrame(seq_num); ) {
    buffer_[index]->continuous = true;                // ① 置连续
    if (buffer_[index]->is_last_packet_in_frame()) {  // ② 末包到了才尝试组帧
      // ③ 往回搜帧首：
      //    - H264：不信任 frame_begin（bug 7106），按"前包存在 + 同 timestamp"回溯
      //      可能吐出从中间开始的不完整帧
      //    - 非 H264：按 is_first_packet_in_frame 回溯
      // ④ 非关键帧缺口检查：
      if (!is_h264_keyframe && missing_packets_.upper_bound(start_seq_num)
                               != missing_packets_.begin()) {
        return found_frames;                          // 帧内有缺口 → 不组（H264 关键帧是例外）
      }
      // ⑤ 组帧：move 出缓冲（槽位置空）+ 重写首尾标记（不信任 depacketizer 的）
      for (i = start_seq_num; i != end_seq_num; ++i) {
        packet->video_header.is_first_packet_in_frame = (i == start_seq_num);
        packet->video_header.is_last_packet_in_frame = (i == seq_num);
        found_frames.push_back(std::move(buffer_[i % buffer_.size()]));
      }
    }
    ++seq_num;                                        // ⑥ 继续查下一个 → 一口气吐出连续多帧
  }
  return found_frames;
}
```

## 五、几个关键机制

### 5.1 缓冲容量：动态扩容，不是固定 2048

```
构造 512 → 槽位冲突时 ExpandBufferSize() 翻倍 → 512/1024/2048
到 2048 还冲突 → 清空整个缓冲 + buffer_cleared
（容量 2 的幂，保证 seq % size 环形映射正确）
```

### 5.2 组帧即移出：缓冲是"只留组不出帧的包"

组帧成功的包 `std::move` 出缓冲、槽位置空。缓冲里剩的是"没资格组帧"的：缺包的、没等到末包的、乱序等待的。**实际占用通常远小于 2048。**

### 5.3 buffer_cleared：清缓冲 = 该要关键帧

缓冲被清 = 半截帧和等待中的包全没了 = 组帧链断裂，后续帧即使组出也解码不了。语义：**对端重新发一个关键帧才能恢复出画**。标准 WebRTC 里 OnInsertedPacket 检查它 → 请求关键帧（PLI 前奏）；课程 5.5 暂时没消费，8.x 用上。

### 5.4 H264 特例：帧首标记不可靠（WebRTC bug 7106）

```cpp
// In the case of H264 we don't have a frame_begin bit (yes,
// `frame_begin` might be set to true but that is a lie). So instead
// we traverse backwards as long as we have a previous packet and
// the timestamp of that packet is the same as this one. This may cause
// the PacketBuffer to hand out incomplete frames.
// See: https://bugs.chromium.org/p/webrtc/issues/detail?id=7106
```

H264 组帧回溯**不信任 frame_begin**，改按 timestamp 回溯 → 可能吐出"从中间开始"的不完整帧。所以 RtpFrameObject 只拿首末 seq——它知道帧可能不完整，下游（解码端）自己判断。配套：**非关键帧组帧前查 missing_packets_ 有缺口就不吐，但 H264 关键帧例外**。

### 5.5 video_payload 为什么没填：SFU 不消费帧数据

`OnReceivedPayloadData` 的 `codec_payload` 参数（depacketizer 解析出的真正编码数据）**传了但被忽略**，`Packet::video_payload` 从头到尾没被填。因为 5.5 的 RtpFrameObject 只拿 `首seq/末seq/codec/video_header`——**SFU 不拼帧、不解码，转发的是 RTP 包（7.x）**。这个字段是给完整接收端（客户端线）预留的。

## 六、5.5 预告：OnInsertedPacket 切帧

```cpp
// 5.5 的 OnInsertedPacket（当前 5.3 是空体）：
for (auto& packet : result.packets) {        // 遍历包集合
    if (packet->is_first_packet_in_frame())  first_packet = packet.get();  // 帧开始
    if (packet->is_last_packet_in_frame()) { // 帧结束
        OnAssembledFrame(std::make_unique<RtpFrameObject>(
                    first_packet->seq_num, last_packet->seq_num,
                    first_packet->codec(), first_packet->video_header));
    }
}
```

即：**packets 按首/末标记切成一帧一帧 → 每帧一个 RtpFrameObject（帧的元信息对象，无 payload）→ OnFrame 回调**（5.4 是 RtpFrameObject 定义，5.5 是回调链路）。

## 七、一句话记忆

> **5.3 = 把线上包变成缓冲单元（Packet 只拷 RTP 头 + video_header），喂进 PacketBuffer 环形缓冲（512 动态扩到 2048），InsertPacket 内部用"两触发三闸门"识别完整帧，FindFrames 组帧即移出并重写首尾标记；返回的 InsertResult.packets 是完整帧的包集合（可能连续多帧），buffer_cleared 是"清缓冲了，要关键帧"；H264 帧首标记不可靠（bug 7106），按 timestamp 回溯可能吐不完整帧；video_payload 全程没填——SFU 不消费帧数据，转发的是 RTP 包。**
